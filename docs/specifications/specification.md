# 系统规格书

版本：D0.15；日期：2026-09-29；状态：保存与项目协作规则部分已确认，业务联动仍按对应待决项讨论。

## 通用约定

- API 路径为接口设计草案，当前没有这些接口。
- 请求身份由服务端会话解析，客户端不能提交 actor_id 冒充操作人。
- 写请求只接受白名单字段，明确校验规则。服务端生成提交时间与新版本。
- 校验独立输入后再修改数据；失败不改变业务和审计状态。
- 返回统一错误码、可理解信息、request_id，保留用户输入。400 为输入结构错误，401 为未认证，403 为禁止操作，404 为对象不存在，409 为版本/业务冲突；暂定 422 表示业务字段校验失败。
- 文档中的“必须”用于规定目标实现，不表示今天已具备该能力。

## SPEC-001 身份认证与会话

输入：登录名与凭据。前置条件：账号启用且未触发限速。

处理：验证密码哈希，创建随机会话；持久存 token_hash，安全 Cookie 保存随机标识。Cookie 使用 HttpOnly、Secure、明确 SameSite；写接口校验 CSRF。失败响应避免泄露账号是否存在。

输出：本账号身份和会话有效信息。登录态恢复仍需服务器验证，退出、改密、停用按策略撤销会话。会话期限与多设备策略见 Q-010。

接口草案：`POST /api/auth/login`、`POST /api/auth/logout`、`GET /api/me`。未认证请求不得读取业务数据和报告下载。

## SPEC-002 保存、事务、并发与审计

### 明确保存

用户确认：普通文字、信号灯、优先级、阶段、结案等一切业务信息修改，都必须点击“保存”后提交。选择、输入、拖动、失焦、切页、计时或接收通知不能自动提交；新增/删除子记录、节点位置和关联变更也属于修改。操作表单中可显示“保存阶段变更”“保存结案”等明确文案，不能仅点选状态就生效。取消不改变正式数据。

输入：业务动作参数、进入详情时取得的 expectedVersion；创建及可重复副作用动作携带幂等键。权限依据 SPEC-014。

处理：验证身份与输入 → 在短事务内核验当前项目负责关系及版本 → 按 ID 与版本条件更新 → 写业务子表和审计 → 提交 → 返回已保存数据与新版本。负责关系变更与业务写入采用同一项目并发边界，避免“检查有权后权限被撤销仍提交”的竞态。更新行数不满足预期时回滚并返回冲突，不静默覆盖。

幂等键按用户和操作范围约束；同键同请求返回原结果，同键不同内容返回冲突。幂等结果与业务提交的一致性必须有测试。

失败：数据库或审计失败时回滚；响应丢失后通过幂等结果确认是否已经提交。版本冲突返回 409，提示“项目已被他人更新，请重新进入项目”，不得把旧输入换一个新版本号继续提交，不自动合并或强制覆盖。用户已确认：保留未保存文字供复制，禁用旧版本保存；点击重新进入前提醒未保存内容不会自动带入新版本。

接口草案：`PATCH /api/projects/{id}` 仅更新普通字段；生命周期变化通过专用动作。项目级 version 统一保护子对象写入，初期接受较粗的冲突范围。

### 进入详情后的固定版本

1. 进入项目时获取同一已提交版本的项目数据、子记录与版本号。技术实现以短事务/一致性读取取得完整视图，不为用户停留页面而长期保持数据库事务或锁。
2. 页面显示进入时的数据；其他人的编辑内容不广播，其他人的保存结果也不自动替换此详情。只读进入同样遵循固定视图。
3. 发现项目版本已变化时，显示上述提示并使旧页面不能保存；用户点击重新进入，重新读取最新数据及权限。不要求先显示字段差异。
4. SSE 未送达时，重连、页面聚焦及保存前的服务端校验仍能发现变化。无法确认服务端状态时不得显示保存成功。
5. 同版本的两个并发提交只允许一个成功；不同字段、同账号不同标签页的旧版本提交也不能绕过校验。
6. 本页自己的保存成功后，以服务端返回数据和新版本建立下一次编辑基线；通知带本次提交标识，避免把自己的成功保存误报为他人更新。
7. 看板列表可刷新摘要；已打开详情仍保持其版本并提示过期。在线编辑名单独立刷新，不改变业务数据版本。

个人页面位置等浏览偏好与业务修改区分；它们的自动恢复不构成业务保存。系统设置表单是否也需逐项保存、个人草稿是否自动持久化，仍按 Q-017 明确；未确认前不把自动草稿写入当作业务已保存。

## SPEC-003 项目生命周期与阶段

动作草案：createProject、startProject、pauseProject、resumeProject、startStage、completeStage、rollbackStage、closeProject、reopenProject、setMaintenance。

每个动作校验当前状态、版本、必要说明和关联数据，使用 SPEC-002 提交；跨状态操作不能靠任意字段 PATCH 绕过。

| 动作 | 规则及确认状态 | 决策或待决项 |
|---|---|---|
| 启动 | S1 完成后人工启动，确认实际启动与预计结案日期并保存 | DEC-027 |
| 开始阶段 | 已确认选择 B：前置满足后只解锁，负责人点击开始并保存后进入进行中 | DEC-023/024/027 |
| 完成阶段 | 已确认严格串行；保存完成只解锁下一阶段，不自动开始；纠错与日期按本节确认规则；完成所需业务材料待另行明确 | DEC-024 |
| 暂缓 | 保存原因与此前状态，保留计划和成果，禁止推进和真实回退 | DEC-028 |
| 恢复 | 复核计划并恢复此前状态，不重新生成阶段开始记录 | DEC-028 |
| 正常结案 | 人工确认交付和遗留事项处置，保留真实阶段进度 | DEC-029 |
| 中途终止 | 记录原因、结案日期及遗留事项，保留真实状态 | DEC-029 |
| 重新打开 | 保存原因，恢复结案前状态，保留结案历史 | DEC-029 |
| 开启量产维护 | 仅已结案可用，不自动重开研发 | 延续原业务含义 |

### 项目状态与阶段联动（已确认）

用户回复“确定”，确认本轮启动、暂缓恢复、结案重开三块方案（DEC-027/028/029，Q-001/003/004 已解决）。本节补充项目总体状态对阶段操作的限制；完整逾期公式、时区及其他未讨论规则不在本次批准范围。

#### 新建、S1 与正式启动

沿用“先做 S1 需求立项，再进入正式执行”的业务顺序，但将自动改变项目状态改为明确人工启动：

1. 新建保存后为提案中，S1 待开始，其余阶段未解锁；录入账号自动负责。名称必填，客户等资料允许逐步补齐，真实新建不借状态下拉直接指定已结案或已完成阶段。
2. 提案中允许负责人开始 S1、完成 S1，均需明确保存；完成后 S1 已完成、S2 待开始，项目仍提案中。此时 S2 显示“需先启动项目”，不能开始；阶段前置满足不等于项目已获准执行。
3. 负责人选择“启动项目”，核对项目实际启动日期、预计结案日期及项目名称，点击保存后改为进行中。S1 须已完成；启动日期可补录过去真实日期，不能早于 S1 实际完成日期，未知历史数据走迁移核对；预计结案日期不能早于实际启动日期。客户等其他字段不新增强制门槛，至少一位负责人由当前操作权限保证。
4. 启动项目不自动开始 S2；负责人再按 B 开始 S2 并保存。项目启动日期与 S2 开始日期分别记录，允许先确定正式执行、稍后实际开工。
5. 已进行中的项目因返工回退至 S1 时，项目总体仍进行中，S1 待开始；不自动变回提案或重写首次项目启动日期。新建初始化与后续返工不能混为一条规则。

“启动项目”是已确认的独立人工动作；旧代码 S1 自动改项目状态的行为不沿用，源码事实见系统真相。

#### 暂缓与恢复

提案中/进行中都可暂缓，保存原因并记录此前项目状态；阶段状态、阶段日期、进度和已有成果保留，页面明确显示项目暂缓，不把保留的阶段进行中当成仍在执行。

暂缓期间允许保存文字、计划、说明、灯色、紧急程度及事实纠错，继续遵守权限、版本和日期顺序；不允许正式启动、开始阶段、完成阶段或真实返工回退。纠错用于修正既有事实，不能借普通字段修改把项目恢复或代替新的推进动作；本节不要求判断用户业务说明的真实性。

负责人保存“恢复”后回到暂缓前的项目状态，阶段继续使用保存的状态：原来进行中的仍进行中，原来待开始的仍待开始，不额外生成阶段开始记录。恢复前展示计划供核对；改期必须明确修改并保存。

暂停不自动顺延计划、不扣除日历天数；暂缓标签单独展示。完整逾期公式、参与状态和时区仍由 Q-005 确认，不因本次暂停规则获批就视为完整逾期规则已确定。

#### 结案、量产维护与重新打开

保留项目状态“已结案”，结案表单由人选择“正常完成”或“中途终止”，必填结案说明并确认实际结案日期，允许符合真实情况的历史补录，服务器另记操作时间。显示未完阶段、节点和未关闭风险供核对；有遗留事项时填写其处置说明，不静默删除或标为完成。

系统不根据所有节点完成、红黄绿或阶段数量自动结案，也不要求七阶段全部完成才可提交结案。负责人对实际交付结果作判断，系统负责输入及一致性检查。因此实际阶段进度可能低于 100% 而项目已结案；正常完成与中途终止在统计中应能区分，阶段进度不能当作结案率。

结案后保留真实阶段状态和进度，以项目已结案状态禁止新阶段开始/完成/真实回退。允许负责人补充说明和纠正文字、日期等事实；涉及有效阶段状态变化时先走重新打开，不能直接改总体状态绕过记录。正常结案与中途终止不自动打开量产维护。

旧模型的 S7“MP量产维护”是阶段名称，“已结案后的量产维护”是另一个标识。首版保留两者：前者记录阶段工作，后者用于结案后的持续支持；开启维护不重开项目或重置阶段，操作范围另按节点/风险规则确认，不能因此开放研发阶段推进。

重新打开由负责人填写原因并保存，恢复结案前的项目状态和当时阶段状态（包括原暂缓情况），关闭仅对已结案有效的维护标识并保留历史。若目的是回到较早阶段重做，再按已确认回退操作选目标，保存后待开始；原结案记录不抹除。结案前全部阶段已完成时，重新打开不凭空启动阶段，需要明确回退目标。不得把重新打开等同于自动开工。

#### 统一保存与验证边界

上述动作全部走 SPEC-002/014；同一次操作的总体状态、相关日期、原因与历史必须原子保存。普通字段接口不能直接改变总体状态绕过动作校验。测试预期见 TEST-023/024/025；本轮仅确认规则，没有执行业务验收，也不新增审批人或审批流。

### 已确认的阶段顺序约束

前一个阶段未结束，不能开始后面的阶段（DEC-022）。普通操作、接口调用、导入、历史补录和纠错都必须维护这一顺序，不能仅靠按钮隐藏。后端不得接受前置未完成、后续却处于有效已开始/已完成状态的提交；导入异常应报告，不静默改成完成。未来阶段的计划安排与实际开始分开，填写计划不代表启动阶段。

用户已选择手动开始（DEC-023，Q-020 已解决），具体状态转换见下文。旧代码首个未完成阶段不能直接映射为已经实际启动；实际业务日期与保存操作时间须区分，日期处理见下文已确认规则。

### 阶段纠错、日期及进度（已确认）

用户回复“1、确定”，确认上一轮整块纠错、日期处理、资料保留及旧版进度映射方案（DEC-024，Q-002 已解决）。本节适用于误填信息和误记动作。真实返工使用下文“回退”入口，保留曾经完成的事实。

此前允许前置未完成而后续仍有效完成的方案已撤回。项目启动、结案仍由人确认，不随阶段纠错隐式改变；跳过或不适用不在当前规则内。

#### 入口与结果

“修改阶段信息”“撤销开始”“撤销完成”分开。只有项目负责人可以保存纠错，纠错理由必填；全部遵循 SPEC-002 的版本与事务校验。保存前展示所有受影响阶段的旧状态、新状态和有效日期变化；只预览不写数据。用户一次点击“保存纠正”提交整块结果，不要求逐阶段分别保存。

| 情况 | 确认处理 | 后续阶段与日期 |
|---|---|---|
| 文字、计划或实际日期填错 | 修改指定信息，保留阶段状态 | 实际日期违反顺序时指出冲突，不静默移动其他阶段日期；计划变更不推导实际开始 |
| 当前阶段误点开始，尚未完成 | 撤销开始，回到待开始 | 清空本阶段当前有效实际开始日期；旧值留审计；后续保持未解锁 |
| 当前阶段误点完成，下一阶段尚未开始 | 撤销完成，回到进行中 | 保留本阶段有效开始日期，清空有效完成日期；下一阶段从待开始回到未解锁 |
| 较早阶段误记完成，后续已有开始或完成 | 预览后整体回退：目标阶段恢复进行中，其后阶段全部未解锁 | 目标阶段保留开始日期、清空完成日期；后续清空当前有效开始/完成日期，旧状态与日期留审计 |

目标阶段若连开始记录也是误填，可在同一纠错预览中明确选择回到“待开始”，同时清空其当前有效开始/完成日期，后续均未解锁；不能只取消完成而保留错误的开始。旧数据缺失可靠开始信息时报告待核对，不能凭回退动作补造时间。

全部变动必须在同一次保存后构成合法串行状态。预览期间其他人保存导致版本变化时拒绝整次纠错，不能使用旧预览覆盖最新项目。

#### 保留内容与联动范围

节点、阶段评述、已有成果、风险与变更记录均保留，包括原来的节点完成记录。撤销阶段不等于这些记录也填错；若其中某条记录本身错误，应单独纠正。页面须区分保留的历史记录与当前阶段状态，历史评述不能自动作为下一次完成的确认说明。

计划日期保留，不因回退自动整体顺延。红黄绿、紧急程度和项目负责关系保持原值；项目总体状态不由阶段纠错隐式切换。已结案项目重开、暂缓时的操作限制见上文已确认项目状态联动，不能通过阶段纠错绕过。

保存后自动更新当前阶段展示、后续解锁资格及按已确认算法派生的进度；下一次开始仍按 B 另行保存。审计记录操作人、服务器保存时间、纠错理由及全部旧值/新值。看板与新请求使用保存结果；其他已打开详情按固定版本机制提示过期。

#### 实际日期规则

- 正常开始/完成表单默认当天，可在保存前改成真实发生的过去日期；只填写日期不产生状态转换。未来日期只用于计划。
- 业务实际日期按天记录；服务器另记精确的操作时间，补录不能修改审计时间。
- 同一阶段开始日期不得晚于完成日期；后阶段开始日期不得早于前阶段完成日期。同一天完成和开始允许，不要求相隔一天。
- 修改较早阶段日期造成与后续冲突时，展示冲突并拒绝该次保存，用户先核对真实日期；系统不自动挪动其他阶段日期。需要同时改多个日期时在同一预览与保存中校验完整结果。
- 缺失的历史日期保留未知，不把导入日或首次访问日当作实际日期；历史补录与普通推进的校验范围在迁移映射时明确。

#### 进度规则

采用旧版完成映射：S1 完成 5%、S2 完成 10%、S3 完成 20%、S4 完成 60%、S5 完成 80%、S6 完成 90%、S7 完成 100%；没有完成阶段为 0%。这是阶段完成后的累计值，不是各阶段相加。开始或等待阶段不额外增加比例。

示例：EVT 已完成、DVT 进行中时为 60%；撤销误记的 EVT 完成后，EVT 进行中、DVT 未解锁，按该映射回到 20%。不手工单独修改百分比。

### 真实返工的回退入口（已确认待开始）

用户确认业务存在真实返工，并提出“回退选项 + 联动具体阶段栏 + 原因”（DEC-025）。采用这一简洁入口，不新增返工子项目、审批或独立任务流程。仅选阶段或输入原因不产生修改，仍须明确保存。

交互：选择“回退” → 显示“回退到的阶段”下拉和必填“回退原因” → 预览受影响阶段及进度 → 点击“保存回退”。目标必须是本项目此前已完成的阶段，不能选择尚未走到的阶段、借回退前进或绕过前置。保存后状态按下文 DEC-026 执行。

历史记录将动作标为“阶段回退”，区分信息纠错；记录回退前所处阶段、目标阶段、原因、操作者、保存时间及相关状态/日期旧值。每次回退追加记录，不覆盖上一次原因。真实发生的开始/完成记录作为历史保留，不能标成从未发生；当前流程状态与历史事实分别表达。数据表达归 ERD。

后续阶段不能继续保持与目标冲突的有效开始/完成状态。已有节点、成果和说明保留，不因回退自动删改；节点完成记录不能自动完成重新推进的阶段。权限、项目版本、原子保存、审计和过期通知复用 SPEC-002/014。暂缓时先恢复，结案后先重新打开，再按实际项目状态执行回退；不能绕过上文状态限制。

用户选择“待开始”（DEC-026，Q-021 已解决）：保存回退后，目标阶段为待开始，其后全部阶段为未解锁；目标之前已完成的阶段保持原状态。目标及其后阶段的当前有效实际开始/完成日期清空，原真实日期和完成事实保留历史；计划日期与已有资料保留。负责人另行点击开始并保存，以记录本次实际开始，回退保存时间只进入审计，不能当作实际开工日期。

示例：DVT 进行中时回退至 EVT，保存后 EVT 待开始、DVT 及后续未解锁，进度按保留的 S1～S3 完成状态回到 20%；重新开始 EVT 不增加进度，完成 EVT 并保存后才恢复 60%，DVT 随后待开始。

本决定只规定真实返工的“回退”动作。误点完成后的“撤销完成”仍按上文纠错规则恢复进行中并保留原有效开始日期，不能将两种动作混为一项日期处理。

### 阶段开始与更新（已确认 B）

Q-020 已解决，用户选择 B（DEC-023）：保存当前阶段完成后，只解锁下一阶段；负责人点击“开始”并明确点击“保存”后，下一阶段才进入进行中。以下为目标契约，旧代码尚未实现。

| 阶段显示 | 含义 | 正常推进动作 |
|---|---|---|
| 未解锁 | 前置阶段尚未完成 | 不能开始或完成；填写计划不改变状态 |
| 待开始 | 前置已满足，但没有保存开始动作 | 负责人选择开始并保存 |
| 进行中 | 开始动作已经保存，尚未完成 | 负责人确认完成并保存 |
| 已完成 | 完成动作已经保存 | 后续纠错按本节，不直接改写历史 |

未解锁/待开始可由前置状态与本阶段状态派生，不要求数据库重复保存四份标志。正常流程不能从待开始直接跳成已完成，也不能同时有两个进行中阶段。首阶段没有上一阶段，初始化及与人工启动项目的关系见上文；新建项目时 S1 待开始。

示例：EVT 进行中 → 保存 EVT 完成 → EVT 已完成、DVT 待开始 → 负责人点击 DVT 开始并保存 → DVT 进行中。等待期间明确显示“DVT · 待开始”，不能显示正在进行，也不能伪造 DVT 已实际开始。

阶段开始和完成均遵循 SPEC-002/014：校验负责范围、项目版本和前置条件，事务保存阶段变化、操作人、服务器操作时间及审计，成功后通知其他页面。重复操作不得推进两次；取消、未保存、保存失败和冲突均不产生阶段变化。

日期录入、到达日期、节点完成、信号灯和优先级变化均不能代替开始/完成动作。实际日期默认、历史补录及纠错按本节已确认规则；保存时间不能冒充历史实际发生时间。阶段开始本身不新增完成进度。

全部阶段完成后没有下一阶段可解锁；项目结案仍走人工结案流程。暂缓、结案状态下允许的动作见上文项目状态联动，不能绕过项目生命周期。

## SPEC-004 日期、计划和派生状态

候选模型：original_due_date 保留原始计划，current_due_date 代表现行计划，schedule_changes 记录改期过程。补充说明与有效改期有不同语义。

`rescheduleProject` 必须提交有效新日期及原因。追加说明不得修改 current_due_date。历史最后一条为空不能导致当前计划丢失。

候选逾期公式：项目处于需要追踪交付的状态且公司业务日期晚于有效计划日期。没有有效日期时显示“计划未定”，不能默认为正常。暂缓不自动顺延计划已确认；参与逾期统计的项目范围统一在 Q-005 中确定。

历史改期、当前逾期和人工风险分别提供字段与解释。看板、详情、统计、导出调用同一领域规则；不在各页面复制不同公式。

阶段进度映射已按 DEC-024 确认，唯一正文见 SPEC-003；终止保留真实阶段进度，显示规则见 SPEC-003；未定义跳过状态。

## SPEC-005 风险、节点、变更和检查

风险新增保存内容和等级；解除保存处理结果、操作人和时间，保留原始内容。责任人、审批或复开行为待 Q-012。

节点包含项目/客户类型、目标日期、完成结果；连线与阶段引用必须属于当前项目。需求变更保留原事实和决定；是否进一步联动计划由规则确认，不能隐式改日期。

访问详情不更新业务检查记录。建议 `confirmCheck` 明确提交结论，产生 project_checks 记录；检查状态是派生结果，不覆盖业务更新时间。Q-006 未确认前标记为建议。

## SPEC-006 基础资料与引用

用户维护客户、工程师、芯片、产品线、APP、标签、分组和企业信息。新项目使用稳定 ID 引用；页面展示名称。

改名后当前展示可更新，历史审计保留当时名称；停用后旧项目仍可读取，新选择器默认不提供停用项。有引用的数据禁止直接级联删除。

旧系统名称映射沿用 NFKC、大小写和空白归一化作为候选匹配依据，但冲突必须明确展示，不把不同人员或芯片静默合并。

## SPEC-007 工作状态与草稿

偏好按用户和页面保存；滚动位置可按设备/标签页保留，避免另一设备反复覆盖当前阅读位置。详情重新进入必须读取最新版本及权限，不能恢复旧缓存并允许直接编辑；固定视图与过期处理见 SPEC-002。

如采用持久草稿，保留 base_version，不能直接覆盖正式数据。重新登录后仅同一账号可恢复。账号切换清理本机敏感缓存；是否自动保存草稿及其期限待 Q-017。冲突时保留当前页面文字供复制，不代表刷新后仍持久保留草稿。

网络中断不显示已保存；恢复后检查身份、项目负责关系与版本。过期版本必须重新进入；恢复网络、恢复会话均不能自动提交。新版本提醒不自动替换正在编辑的业务数据。

## SPEC-008 会议、统计与报告

报告输入包含项目范围、字段、筛选、报告名称及格式。建议固定生成时快照，记录生成账号和时间；导出读取相同快照，避免过程中读取多个不同版本。

多行状态、人员、芯片、维护标识、项目备注等按选择输出。HTML/Markdown/CSV 各自正确转义，CSV 需评估公式注入处理且不破坏业务原文。下载结果可追溯并受认证保护。

会议开始、暂停、继续、结束均是业务动作；计时依据保存的时间点，浏览器关闭不丢会议。会议与报告的最终数据结构仍需 Q-012 确认。

结果必须可下载或供下一步汇报消费。任务状态成功但产物无法下载不算完成。

## SPEC-009 导入、迁移与删除恢复

输入：旧 JSON 原文件、明确来源、备份 schema 版本和冲突策略。

预检：容器结构、语义 ID 重复、名称引用、非法阶段、缺失日期、旧字段及业务备注；输出逐项映射和未解决项。无预检确认不得执行覆盖导入。

提交：限定导入范围；对小批量以事务整体提交，失败回滚；大批量策略待数据规模确认。导入与在线编辑冲突需检查版本或在明确维护窗口执行。

验证：新请求逐项读回，项目数、关键值、关联和历史对账，再核对看板及导出。

建议删除先进入回收站；恢复重新校验引用和版本。完整数据库恢复与普通项目恢复分开，前者按运维流程执行，不开放为随手点击的业务按钮。

## SPEC-010 后台任务与重试

仅在确认任务需要异步时实施。任务状态：queued → running → succeeded / failed；失败可按策略重试，具体重试次数、超时及保留期限待任务类型确定。

收到任务 ID 仅表示已受理，不表示完成。状态接口必须给出任务类型、发起人、进度含义、结果和可用恢复动作。

若使用 Redis + BullMQ：提交与投递之间可恢复、任务执行幂等、产物写入有确定标识、进程崩溃可重试；同一任务不能重复改业务、重复生成被误认为不同的记录。重任务与交互请求分进程，限制并发。

未引入队列时不编写空的队列适配框架。需求明确后依据实测选型。

## SPEC-011 部署、升级与恢复

测试入口公网 HTTPS，前后端同站点；MySQL 和可选 Redis 内部访问。账号和数据库凭据通过运行配置注入，不进入 Git。

版本化构建物包含代码提交标识；数据库迁移有独立版本。升级先验证备份和兼容性，再迁移、部署、检查健康、执行真实业务回读。

应用回退使用上一可兼容构建物；数据库恢复需独立方案，不能自动覆盖发布后数据。更新策略详见[发布维护](../operations/release-maintenance.md)。

## SPEC-012 性能与容量

以下为建议目标，待 Q-007、Q-011 及代表性数据确认后成为发布门槛：

| 指标 | 候选目标 | 测量范围 |
|---|---|---|
| 已加载列表的筛选/视图切换 | 交互反馈约 100 ms 内 | 浏览器本地，不含首次数据获取 |
| 普通业务 API | 服务端处理 p95 ≤ 200 ms | 排除导入、报告等重任务，包含正常数据库访问 |

测试报告记录数据规模、预热、持续时间、请求数、p50/p95、错误率、服务器资源和网络。首次登录、冷启动和大历史详情单独测量。现有服务器共享其他负载，未压测前不声明容量通过。

## SPEC-013 文档、模块和验收治理

## SPEC-014 项目负责范围与编辑授权

已确认：四个账号均可查看和搜索全部项目；仅负责范围内的项目可修改；一个项目允许多人共同负责。相同管理员身份不绕过项目编辑范围。项目 PM、硬件/软件负责人、参与人等原业务字段不自动成为系统授权依据。

创建项目：点击保存后，在同一事务创建项目、以当前登录账号记录 created_by，并建立该账号的项目负责关系；由服务端确定身份，不能由客户端指定冒充。失败时整体回滚。created_by 与现任负责人关系分开保存。

负责范围：用户可自行加入或退出任意项目的本人负责关系，无须其他负责人审批，允许多人负责。设置需点击保存并落到服务器，不能用看板筛选或本地勾选代替授权。加入后读取最新项目版本再编辑，退出后恢复只读，其他人的负责关系保留。身份由会话确定，自助接口不能改动其他账号的负责关系；加入/退出写入审计。最后一位负责人退出后的业务处置仍待 Q-015。

所有修改入口均校验负责范围，包括普通字段、阶段、纠错、节点、风险、延期、项目备注和批量写入。未负责项目呈只读，直接构造写请求也返回 403；混合包含无权限项目的批量请求不得暗中跳过后报告全部成功。全局基础资料、账号和系统维护权限另见 Q-016，不以本节推导任意全局权限。

存量项目负责人的首次分配不能从旧 pm/hwOwner/swOwner 名称自动授予账号权限，也不能把导入者虚构为全部项目原始创建人，见 Q-015。

## SPEC-015 正在编辑提示

已确认：项目详情实时显示哪些人正在编辑该项目，不显示编辑字段、实时输入或修改细节；仅查看不应被误报为编辑。

工程建议：有权用户进入编辑操作时登记编辑状态；结束编辑、离开、退出登录或权限失效时撤销，异常断网通过短期心跳过期清理。显示当前有效编辑者名单，能表达连接中断时状态未知。编辑开始/结束通知不等同于业务保存，无须用户保存心跳。

编辑状态绑定可信账号、会话、项目和页面实例，跨标签页分别管理并按用户汇总显示。载荷仅包含身份展示和编辑状态，不包含未提交的业务值。后端登记时检查权限。

首版单常驻进程可用内存保存短期在线状态，通过 SSE 分发；进程重启后由页面重新登记。在线名单不写入项目业务版本、不产生逐次心跳审计，也不作为互斥锁或保存成功依据。实际数据冲突始终由 SPEC-002 的数据库版本校验处理；不因此引入 Redis 或协同文本编辑框架。


## SPEC-016 完整备份与恢复契约

用户要求真实备份覆盖所有数据。工程定义为可恢复完整系统持久状态：项目及子记录、基础资料、账号与负责关系、会话/审计、个人偏好、已实现的持久草稿、共享备注、企业设置、会议、报告记录及其文件产物；未来新增持久实体须进入备份清单。没有实施的能力不虚构备份内容。

备份清单记录备份时间、一致性边界、软件与 schema 版本、数据库和文件校验信息、受控运行配置的恢复依赖。数据库与外部产物须对齐到可恢复的一致边界。凭据及敏感配置受控保存，不进入 Git；恢复后会话按恢复策略撤销或重新认证，不无条件恢复旧登录权限。

短期在线编辑心跳等运行态在恢复后重新登记。未点击保存的页面输入不是已提交业务数据；如确认持久草稿，则其持久内容纳入清单。

验收在隔离环境恢复，核对实体/关联/文件与关键值，再执行新请求读取及页面/报告消费。原始备份只读保留。现有 V1.044 文件须与原系统持久来源对账，不能凭项目数宣布全量。频率、保留期限、恢复目标和操作步骤归发布维护文档。


## SPEC-017 红黄绿信号灯（沿用 V1.050）

状态：用户确认沿用原代码的灯色逻辑；服务器写入同时遵循 SPEC-002/014 的显式保存、项目负责范围与版本校验。

字段：signal 为绿灯/黄灯/红灯，signalNote 为文字备注。原版新建默认绿灯、备注为空。用户通过下拉框选择灯色并保存，程序没有按日期、风险数量、阶段或优先级自动判灯的公式。

| 灯色 | 原页面供人工参考的说明 |
|---|---|
| 绿灯 | 进度正常；延期＜7 天；关键问题有责任人和计划；客户需求稳定；无阻塞 |
| 黄灯 | 预计延期 7–14 天；关键问题未关闭但有方案；需求有变更；任一环节有风险 |
| 红灯 | 延期＞14 天；无解决方案；负责人资源冲突；客户重大投诉；关键物料缺料 |

这些描述供人综合判断，代码未规定条件之间是且/或，也未实现优先级或冲突裁决。不能把该表转成自动规则。红/黄灯备注提示填写原因，但原保存逻辑没有将原因设为必填；换灯也不会自动清空或改写旧备注。

保存后影响：详情与看板灯色标签；信号灯维度筛选及启用的统计图；当前看板、筛选和搜索范围内的灯色数量；旧版字段变化历史。符合导出字段选择的输出使用已存灯色/备注，不重新判定。灯色不自动修改项目状态、阶段、进度、日期、priority、isDelayed 或风险记录。重点项目进度排序按 priority 及进度，不能把它解释为按红黄绿排序。

兼容边界：旧 validateBackupData 对缺失/不合法 signal 回退绿灯；正常新建默认绿灯。这些是默认值，不是系统完成了健康评估。迁移预检须保留原值并报告发生的回退，不能据绿灯推断数据已经人工核验。用户此次同意保留灯色业务逻辑，不扩展为确认其他导入字段的默认策略。

源码证据与核查限制见系统真相“信号灯与优先级的当前代码证据”；紧急程度与 priority 的业务对应及统一展示范围已由 SPEC-018 确定。


## SPEC-018 优先级与统一展示范围

状态：用户明确同意优先级沿用和展示范围统一（DEC-020/021）。

优先级：用户所说的紧急程度对应现有 priority，保留高/中/低，人工选择并点击保存。新建默认中，旧数据缺失或非法值的回退中须在迁移预检报告中可见。保留高优先级视觉强调、筛选统计与修改历史；灯色、交期、风险和阶段不自动改变优先级。服务器授权、事务及固定详情版本按 SPEC-002/014 执行。

展示范围：主看板卡片/进度行、顶部统计、启用的分布图及重点项目进度列表，共用“当前看板范围 ∩ 字段筛选 ∩ 搜索结果”项目集合。仅查看某客户时，四个区域均排除其他客户。统计按完整结果集计算，不仅统计分页当前页；同次展示使用一致的数据版本，避免区域之间短暂混用不同结果。

重点项目进度列表在该集合内按高→中→低、同级进度降序排列，不能再暗中改用全部非结案集合；同优先级且同进度时使用稳定的项目 ID 次序作为工程实现。主卡片原顺序不因本次决定自动改为这套排序。处于已结案看板时，重点列表也使用当前范围，不额外排除已结案项目。标题/范围提示随实际范围表达。

提供明确“全部项目”范围用于全局概览，解除看板的状态分区限制；其余仍启用的字段筛选与搜索清楚显示，并继续对所有区域同时生效。清空筛选与搜索后可看全量。查看权限继续为全项目可见，负责范围只限制修改，不自动缩小查询范围。

该规则改变旧版顶部统计、分布图和重点列表范围不同的行为，但不改变红黄绿的人工判断方式，也不改变已经打开详情的固定版本机制。
