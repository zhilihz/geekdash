# 系统规格书

版本：D0.29；日期：2026-09-30；状态：核心契约、首批账号、服务器草稿/容量、详情保存粒度及会话恢复策略已确认，服务器版未实现。

## 通用约定

- API 路径为接口设计草案，当前没有这些接口。
- 请求身份由服务端会话解析，客户端不能提交 actor_id 冒充操作人。
- 写请求只接受白名单字段，明确校验规则。服务端生成提交时间与新版本。
- 校验独立输入后再修改数据；失败不改变业务和审计状态。
- 返回统一错误码、可理解信息、request_id，保留用户输入。400 为输入结构错误，401 为未认证，403 为禁止操作，404 为对象不存在，409 为版本/业务冲突；暂定 422 表示业务字段校验失败。
- 文档中的“必须”用于规定目标实现，不表示今天已具备该能力。
- 首版规则取舍遵循 DEC-048：已确认契约优先；未改定的判断复用 V1.050；重大问题及人工无法纠正的问题优先核查修复。迁移必须增加的认证、授权、事务和版本保护仍实施，不自行新增业务自动推进、审批或完成门槛。旧流程证据见系统真相，新增业务选择仍需说明来源及影响。

## SPEC-001 身份认证与会话

输入：登录名与凭据。前置条件：账号启用且未触发限速。

处理：验证密码哈希，创建随机会话；持久存 token_hash，安全 Cookie 保存随机标识。Cookie 使用 HttpOnly、Secure、明确 SameSite；写接口校验 CSRF。失败响应避免泄露账号是否存在。

输出：本账号身份和会话有效信息。登录态恢复仍需服务器验证，退出、改密、停用按策略撤销会话。会话期限、多设备及密码恢复按下文 DEC-054 已确认契约。

### 首批测试账号（已确认，DEC-050）

新建四个独立业务测试账号与一个专用维护测试账号，不继承其他系统账号。每个账号使用独立随机临时密码，受控交付；明文密码不进入 Git、文档、镜像和日志，不设置公开共享默认密码。登录名在初始化时登记，正式用户名后续确定。

首次使用临时密码认证后只允许完成改密及退出，服务端禁止访问业务接口、报告或 SSE。强制改密状态持久化于 MySQL，刷新、直接构造请求或重启不能绕过。改密成功后清除强制标志、撤销旧会话并重新认证，随后按账号权限使用；改密失败不清除标志。密码只能保存哈希。正式登录名变更保留账号 ID、负责关系和历史身份关联，不通过删号重建迁移人员身份。后续密码重置按下文 DEC-054 执行；重置不改账号 ID 和负责关系。

### 会话与密码恢复（已确认，DEC-054）

允许本人多设备登录，各会话独立验证；本会话连续 7 天未有效使用，或距本次认证达到 30 天，均须重新登录。期限由服务器校验，届满边界即失效；SSE/自动轮询等后台保活不能让无人使用的会话无限延续。正常本人页面/接口操作记录 last_seen_at，写入节流见 ERD；浏览器缓存或其他设备活动不能绕过本会话到期。主动退出撤销当前会话，改密、密码重置或账号停用撤销该账号旧会话并使 SSE 失效。

业务账号忘记密码，由唯一维护账号明确执行重置：产生独立随机临时密码，持久设置强制改密、撤销旧会话并记审计；密码/哈希不进审计或日志，凭据受控交付。失败保持原凭据和会话状态，不显示成功。账号 ID、负责关系、项目数据及历史不随重置变化；使用临时密码认证后仍只可改密/退出，不能读业务。

唯一维护账号无法登录时，由具备服务器权限的操作者通过受控命令恢复登录凭据和必要维护身份，撤销旧会话并记录恢复操作。保持业务关联与历史，不创建公开找回接口、不借恢复转移项目责任。恢复执行环境及操作者登记在受控运维记录，不把凭据写入项目文档。

### 账号停用与交接（已确认前置，DEC-038）

用户选择先完成项目交接才允许停用。账号启用/停用及唯一维护账号变更由唯一维护管理员管理（DEC-043，替代 DEC-040 的多人维护范围）；交接完成标准已由 DEC-041 确认：该账号当前负责的每一个项目（含结案项目）都已有至少一位其他启用中的负责人加入并保存。没有负责项目时该项前置自然满足；已停用账号不计为可用接续人，不能把“停用后再认领”实施为默认。后端按当时负责关系及启用状态验证，缺少接续人时列出阻塞项目并拒绝停用；不要求先删除原负责记录。

工程保护：不能停用本人或最后一个有效账号；后端校验当前账号状态及版本，并发操作也不能留下全部停用的结果。停用与业务审计、会话撤销同事务；保存成功后该账号不能新登录，既有会话及 SSE 失效，后续读写重新校验启用状态。已在停用前提交的数据保留，不通过停用倒撤其合法历史；停用与写入竞态必须形成可验证的一致提交次序。

停用不删除账号、审计、项目资料或原负责关系；名单显示已停用，项目当前阶段、计划、灯色及检查记录不变。停用提交前重新确认全部项目接续资格，并与负责关系变更、相关账号停用形成一致事务次序，避免检查后接续人退出/停用仍提交；不自动随机分配；停用后的正式负责关系及最后退出前置仍按 SPEC-014 执行。该提示不是项目生命周期状态，最后负责人主动退出前置仍按 SPEC-014 执行。重新启用账号的资格和明确保存需遵守同等维护权限，原已撤销会话不能复活；原负责关系如仍存在可恢复其编辑资格，历史期间操作不撤销。

不能从本节推导看见他人密码、无痕改历史或批量替别人加入/退出。密码恢复按 DEC-054；已有账号的增补规模、停用后的基础资料归属和账号删除不在本轮自动化范围。未完成导入批次的明确接管见 SPEC-009 已确认规则。

接口草案：`POST /api/auth/login`、`POST /api/auth/logout`、`GET /api/me`。未认证请求不得读取业务数据和报告下载。

## SPEC-002 保存、事务、并发与审计

### 明确保存

用户确认：普通文字、信号灯、优先级、阶段、结案等一切业务信息修改，都必须点击“保存”后提交。选择、输入、拖动、失焦、切页、计时或接收通知不能自动提交；新增/删除子记录、节点位置和关联变更也属于修改。操作表单中可显示“保存阶段变更”“保存结案”等明确文案，不能仅点选状态就生效。取消不改变正式数据。

输入：业务动作参数、进入详情时取得的 expectedVersion；创建及可重复副作用动作携带幂等键。权限依据 SPEC-014。

处理：验证身份与输入 → 在短事务内核验当前项目负责关系及版本 → 按 ID 与版本条件更新 → 写业务子表和审计 → 提交 → 返回已保存数据与新版本。负责关系变更与业务写入采用同一项目并发边界，避免“检查有权后权限被撤销仍提交”的竞态。更新行数不满足预期时回滚并返回冲突，不静默覆盖。

幂等键按用户和操作范围约束；同键同请求返回原结果，同键不同内容返回冲突。幂等结果与业务提交的一致性必须有测试。

失败：数据库或审计失败时回滚；响应丢失后通过幂等结果确认是否已经提交。版本冲突返回 409，提示“项目已被他人更新，请重新进入项目”，不得把旧输入换一个新版本号继续提交，不自动合并或强制覆盖。用户已确认：保留未保存文字供复制，禁用旧版本保存；点击重新进入前提醒未保存内容不会自动带入新版本。

接口草案：`PATCH /api/projects/{id}` 仅更新普通字段；生命周期变化通过专用动作。项目级 version 统一保护子对象写入，初期接受较粗的冲突范围。

### 进入详情后的固定版本

1. 进入项目时获取同一已提交版本的项目数据、子记录与版本号。技术实现以短事务/一致性读取取得完整视图，不为用户停留页面而长期保持数据库事务或锁。
2. 页面显示进入时的数据；其他人的编辑内容不广播，其他人的保存结果也不自动替换此详情。只读进入同样遵循固定视图。
3. 发现项目版本已变化时，显示上述提示并使旧页面不能保存；用户点击重新进入，重新读取最新数据及权限。不要求先显示字段差异。
4. SSE 未送达时，重连、页面聚焦及保存前的服务端校验仍能发现变化。无法确认服务端状态时不得显示保存成功。
5. 同版本的两个并发提交只允许一个成功；不同字段、同账号不同标签页的旧版本提交也不能绕过校验。
6. 本页自己的保存成功后，以服务端返回数据和新版本建立下一次编辑基线；通知带本次提交标识，避免把自己的成功保存误报为他人更新。
7. 看板列表可刷新摘要；已打开详情仍保持其版本并提示过期。在线编辑名单独立刷新，不改变业务数据版本。

个人页面位置等浏览偏好与业务修改区分；它们的自动恢复不构成业务保存。服务器个人草稿按 DEC-052 自动持久化，行为见 SPEC-007；公共业务设置仍需明确保存，个人显示配置可自动记录。

### 项目详情的保存粒度（已确认，DEC-053）

普通字段、资料选择、业务人员、普通说明、计划参数和正在编辑的子记录统一进入本页编辑副本，点击“保存项目”提交同一聚合变更。子记录弹窗的“确认添加/修改”只更新编辑副本，页面持续显示“项目尚未保存”；删除子记录、改连线或拖动业务节点位置也纳入该副本。服务端接收明确变更集合，而不是覆盖客户端未加载的集合；普通保存拒绝夹带项目生命周期、阶段实际状态或负责关系变更。任一关联或审计失败整体回滚，所有本次普通改动均保持未保存。

开始/完成阶段、纠错、回退、暂缓/恢复、结案/重开、负责范围及明确检查等使用各自操作表单和“保存该操作”按钮，同样受项目统一版本保护。普通编辑尚未保存时先提供“保存项目后继续”“明确放弃普通编辑后继续”“取消本次动作”；保存失败不继续状态动作，不把未保存普通字段暗中夹进动作。先保存普通编辑会取得新版本，再基于该版本重新检查状态动作前置。项目以外页面的独立业务表单仍明确保存，并使用其所属实体版本。

自己的保存成功后更新本页基线；其他页面实例和其他草稿即使同账号，也不能自动换版本继续写入。草稿清理及迟到同步见 SPEC-007；本次收敛不改变他人更新时保留文字、重新进入的既定规则。

## SPEC-003 项目生命周期与阶段

动作草案：createProject、startProject、pauseProject、resumeProject、startStage、completeStage、rollbackStage、closeProject、reopenProject、setMaintenance。

每个动作校验当前状态、版本、必要说明和关联数据，使用 SPEC-002 提交；跨状态操作不能靠任意字段 PATCH 绕过。

| 动作 | 规则及确认状态 | 决策或待决项 |
|---|---|---|
| 启动 | S1 完成后人工启动，确认实际启动与预计结案日期并保存 | DEC-027 |
| 开始阶段 | 已确认选择 B：前置满足后只解锁，负责人点击开始并保存后进入进行中 | DEC-023/024/027 |
| 完成阶段 | 已确认严格串行；保存完成只解锁下一阶段，不自动开始；纠错与日期按本节确认规则；完成所需业务材料待另行明确 | DEC-024 |
| 暂缓 | 保存原因与此前状态，保留计划和成果，禁止推进和真实回退 | DEC-028 |
| 恢复 | 复核计划并恢复此前状态，不重新生成阶段开始记录 | DEC-028 |
| 正常结案 | 人工确认交付和遗留事项处置，保留真实阶段进度 | DEC-029 |
| 中途终止 | 记录原因、结案日期及遗留事项，保留真实状态 | DEC-029 |
| 重新打开 | 保存原因，恢复结案前状态，保留结案历史 | DEC-029 |
| 开启量产维护 | 仅已结案可用，不自动重开研发 | 延续原业务含义 |

### 项目状态与阶段联动（已确认）

用户回复“确定”，确认本轮启动、暂缓恢复、结案重开三块方案（DEC-027/028/029，Q-001/003/004 已解决）。本节补充项目总体状态对阶段操作的限制；完整逾期规则已在后续 DEC-030 确认，唯一正文见 SPEC-004；其他未讨论规则仍按对应待决项处理。

#### 新建、S1 与正式启动

沿用“先做 S1 需求立项，再进入正式执行”的业务顺序，但将自动改变项目状态改为明确人工启动：

1. 新建保存后为提案中，S1 待开始，其余阶段未解锁；录入账号自动负责。名称必填，客户等资料允许逐步补齐，真实新建不借状态下拉直接指定已结案或已完成阶段。
2. 提案中允许负责人开始 S1、完成 S1，均需明确保存；完成后 S1 已完成、S2 待开始，项目仍提案中。此时 S2 显示“需先启动项目”，不能开始；阶段前置满足不等于项目已获准执行。
3. 负责人选择“启动项目”，核对项目实际启动日期、预计结案日期及项目名称，点击保存后改为进行中。S1 须已完成；启动日期可补录过去真实日期，不能早于 S1 实际完成日期，未知历史数据走迁移核对；预计结案日期不能早于实际启动日期。客户等其他字段不新增强制门槛，至少一位负责人由当前操作权限保证。
4. 启动项目不自动开始 S2；负责人再按 B 开始 S2 并保存。项目启动日期与 S2 开始日期分别记录，允许先确定正式执行、稍后实际开工。
5. 已进行中的项目因返工回退至 S1 时，项目总体仍进行中，S1 待开始；不自动变回提案或重写首次项目启动日期。新建初始化与后续返工不能混为一条规则。

“启动项目”是已确认的独立人工动作；旧代码 S1 自动改项目状态的行为不沿用，源码事实见系统真相。

#### 暂缓与恢复

提案中/进行中都可暂缓，保存原因并记录此前项目状态；阶段状态、阶段日期、进度和已有成果保留，页面明确显示项目暂缓，不把保留的阶段进行中当成仍在执行。

暂缓期间允许保存文字、计划、说明、灯色、紧急程度及事实纠错，继续遵守权限、版本和日期顺序；不允许正式启动、开始阶段、完成阶段或真实返工回退。纠错用于修正既有事实，不能借普通字段修改把项目恢复或代替新的推进动作；本节不要求判断用户业务说明的真实性。

负责人保存“恢复”后回到暂缓前的项目状态，阶段继续使用保存的状态：原来进行中的仍进行中，原来待开始的仍待开始，不额外生成阶段开始记录。恢复前展示计划供核对；改期必须明确修改并保存。

暂停不自动顺延计划、不扣除日历天数；暂缓标签单独展示。完整逾期公式、参与状态和时区见已确认 SPEC-004。

#### 结案、量产维护与重新打开

保留项目状态“已结案”，结案表单由人选择“正常完成”或“中途终止”，必填结案说明并确认实际结案日期，允许符合真实情况的历史补录，服务器另记操作时间。显示未完阶段、节点和未关闭风险供核对；有遗留事项时填写其处置说明，不静默删除或标为完成。

系统不根据所有节点完成、红黄绿或阶段数量自动结案，也不要求七阶段全部完成才可提交结案。负责人对实际交付结果作判断，系统负责输入及一致性检查。因此实际阶段进度可能低于 100% 而项目已结案；正常完成与中途终止在统计中应能区分，阶段进度不能当作结案率。

结案后保留真实阶段状态和进度，以项目已结案状态禁止新阶段开始/完成/真实回退。允许负责人补充说明和纠正文字、日期等事实；涉及有效阶段状态变化时先走重新打开，不能直接改总体状态绕过记录。正常结案与中途终止不自动打开量产维护。

旧模型的 S7“MP量产维护”是阶段名称，“已结案后的量产维护”是另一个标识。首版保留两者：前者记录阶段工作，后者用于结案后的持续支持；开启维护不重开项目或重置阶段，操作范围另按节点/风险规则确认，不能因此开放研发阶段推进。

保留与容量（已确认，DEC-055）：未提交 active 草稿不自动过期；用户明确丢弃或对应正式保存后才标记终态。单份 payload_json 的规范 UTF-8 序列化有效载荷上限为 1 MiB（1,048,576 字节），每账号最多 100 份 active 草稿；所有设备合计，更新现有草稿不新增计数。创建/恢复新副本需原子校验名额，跨设备并发不得超额。

超限拒绝本次云同步并显示原因，保留服务器已有稿和本机当前输入，提供清理/复制/导出入口；不自动删旧稿、不截断输入、不把同步失败显示为成功。普通正式保存仍按业务输入限制处理，不能因为草稿同步失败就悄悄提交。已提交/已丢弃稿的自动清理期限和回收站规则仍待 Q-017，暂不启动该类清理。

验证：真实草稿写入后用新会话读回；断网/重启/换账号/多窗口/迟到请求/项目过期/权限撤销/正式保存并发均按本节检查，特别证明自动底稿不会产生正式业务提交。

底稿与个人状态 JSON 都带明确 schemaVersion，按表单/白名单 scope 校验。底稿只承载本人可编辑输入与子记录变更；新子记录用客户端临时键关联，正式保存由服务器生成 ID 并返回映射，不把临时键写成 SQL 外键。更新客户端遇不支持的旧底稿结构时保留复制/导出入口并提示重新核对，不能截断、静默丢字段或自动改成正式业务。具体 JSON 契约随实际 API 产生，归 api 目录并注明代码/结构版本。

## SPEC-008 会议、统计与报告

报告输入包含项目范围、字段、筛选、报告名称及格式。建议固定生成时快照，记录生成账号和时间；导出读取相同快照，避免过程中读取多个不同版本。

多行状态、人员、芯片、维护标识、项目备注等按选择输出。HTML/Markdown/CSV 各自正确转义，CSV 需评估公式注入处理且不破坏业务原文。下载结果可追溯并受认证保护。

会议开始、暂停、继续、结束均是业务动作；计时依据保存的时间点，浏览器关闭不丢会议。会议与报告的最终数据结构仍需 Q-012 确认。

结果必须可下载或供下一步汇报消费。任务状态成功但产物无法下载不算完成。

### 独立卡片审查区（已确认范围，DEC-032）

2026-09-30 用户要求独立入口、卡片审查、有误才修正、正确项选中后批量审查，并明确选择“先进入审查区，确认后写入正式数据”。上传和预检只生成待审数据，不改变正式项目、看板、统计、正式项目历史或每周检查记录。结构预检通过不等于人工已审查。

独立“批量导入审查”入口按导入批次恢复待办。卡片可查看导入内容、预检问题及拟新增/更新的结果；已有项目同时呈现正式值和导入值，避免只看新值无法发现覆盖。以项目及其关联资料作为主要卡片粒度是界面建议，独立基础资料的展示方式在完整字段反推后收敛。

- 有误：进入待审内容纠正，点击“保存待审修正”后仍留在审查区；正式项目不受影响。已选中的内容发生修改时取消该项选择，核对最新内容后再选中。
- 正确：勾选卡片；勾选本身不写正式数据，不自动完成审查。点击“保存所选审查（数量）”前显示拟新增/更新对象、关联影响及未解决问题；明确保存才提交选中项。
- 未选项继续待审，可以分次处理；不能因为一批里大多数正确就自动通过其余卡片。已提交项显示实际结果、正式对象链接、审查人和服务器时间，重试不能重复新增。
- 待审区及其修正、选择和提交结果保存在 MySQL，可在重新登录或应用重启后恢复；纳入 SPEC-016 的全部持久数据备份。正式入库前仍须重新校验已确认业务规则、引用、身份与权限。

审查导入资料表示批准本次导入内容，不等于完成 SPEC-005 的每周检查；入库后项目的检查动作仍须另行确认并保存。系统只自动提示格式、引用、阶段/日期约束和版本冲突，不替人判断风险已经解除、阶段应该完成或项目应该结案。

### 待审内容的协作权限（已确认，DEC-035）

2026-09-30 用户选择“首次入库卡片只由上传者纠正和提交”。四人均可查看所有导入批次及逐项结果；首次入库项目的待审卡片默认仅该批次上传者可纠正和提交；经 DEC-039 明确接管后由当前处理人处理，其他账号只读，不能通过直接请求绕过。上传者来自服务端可信账号及持久批次记录，不根据文件内的创建人、工程师或本地模式判断。

更新已有正式项目的待审卡片仅该项目当前负责人可纠正和提交，上传者身份不另行授予修改权；非负责人可以查看，需要处理时先自行加入负责范围、保存并重新核对。所有写入端重新判定待审项属于首次入库还是已有项目更新，不能信任客户端声明类型。账号/共享资料维护及公共设置权限见 SPEC-001/006/019；数据库恢复与备份维护权限仍待 Q-016 对应运维问题，不由待审权限推导。

卡片纠正须明确保存，服务器校验 review_version。相同账号不同标签页，或有权负责人同时打开相同待审版本，A 保存修正后 B 保留旧输入供复制并提示待审内容已更新；B 不能保存旧版本或提交旧选择，重新进入核对。提交既检查待审版本，也检查目标项目版本与当时负责关系。相同待审项并发提交只能得到一个正式结果，其他请求读回已经提交的结果，不重复新增。

上传者、修正者、审查提交者分别记录可信账号及服务器时间；首次入库在此权限方案下由上传者提交，但仍保存各动作来源，不将上传文件当作原项目创建事实。共享待审内容与本人选中集合区分，不能用另一人的选择冒充本人确认。原上传者不被改写，停用后的明确接管见 DEC-039；不能自动接管。

### 停用处理人后的批次接管（已确认，DEC-039）

用户明确允许填写原因、保存接管并保留历史。首次入库待审项默认由上传者处理（DEC-035）；当前处理人初始等于上传者。只有当前处理账号停用后，其他有效管理员才可查看剩余项、填写原因并点击“保存接管”；处理账号仍启用时不能任意夺取批次。

接管后单独保存当前处理人；原上传者及历次处理人保留来源和追加审计，不重写创建事实。仅当前处理人可纠正和提交未完成的首次入库卡片；原上传者重新启用后不会自动拿回已接管批次。若后续当前处理人也停用，下一次明确接管采用同样前置与历史记录。

接管不直接通过卡片、不入库、不改已提交项目的负责关系；更新已有正式项目的卡片仍按项目负责范围。接管者重新进入、核对最新版后再修正/选择/提交；旧页面及旧选择不能继续提交。新入库负责关系仍属于实际保存入库者（SPEC-014），不能因接管批次就负责之前成功的项目。

批次版本保护并发接管；校验当前处理账号停用、改当前处理人、推进批次权限版本及写审计同事务，并发只允许一个结果。接管与项目提交形成明确先后，读取各项实际结果，不重复入库或遗失成功项；应用重启可回读当前处理人及剩余项。处理资格与待审内容、目标项目版本均需在提交时重新校验，SSE 仅提示变化，不替代服务器授权。


### 并发、引用及待决边界

准备更新已有项目的卡片固定对应的正式项目版本；审查期间他人保存后提示“项目已被他人更新，请重新核对导入信息”，保留待审修正供核对，禁止以旧版本入库。重新读取正式项目并核对合并结果后才可再次提交；即使 SSE 遗漏，提交端也必须校验版本。更新已有项目仍受 SPEC-014 负责范围约束，不能以批量入口绕过授权。首次入库负责及旧来源保留见 SPEC-014 已确认规则，不能自动从旧 PM/工程师授予账号权限。

选中项目依赖的客户、芯片等基础资料必须有明确映射和提交范围，不能让已入库项目引用尚未提交的临时对象；无关或未审的项目不会随关联资料悄悄入库。共享基础资料仅指定维护人员可写（SPEC-006）；非维护人员提交导入时只可复用有效映射，缺失资料留待处理，不能借导入自动创建共享资料。

批量失败策略已确认（DEC-033，Q-022 已解决）：2026-09-30 用户选择“其余项目先入库，仅冲突项留待处理”。提交所选项时分别校验，各项可独立成功；冲突、失权、规则或引用异常项不入库，仍留在审查区并给出原因及恢复入口。结果显示成功数、待处理数和逐项结果，不以单一“成功”掩盖部分失败。成功项不因其他项失败回滚；重复请求或只重试失败项不得再次新增已经成功的项目。

大量数据可以由用户分次选择提交，具体单次限额及是否后台执行由真实规模与测量确定，不因“批量”直接增加 Redis。原有覆盖/叠加策略尚未收敛；逐卡片通过不能被实现为默认整库覆盖，完整数据库恢复仍按维护流程另行处理。

单个项目及其必要关联、审计、待审项成功结果作为一个短事务提交；其中任一步失败，该项整体回滚，不能留下只有主表或没有审计的半个项目。已存在的共享基础资料通过映射复用；新资料按明确维护权限、唯一性及引用约束写入，不能因另一项目失败而删除已经被成功项目引用的资料。共享引用异常时分别阻止依赖该引用的项目，给出具体关联原因；独立项目仍可成功。

批次保存各项实际结果；进程中断或断线后先查已提交结果，再决定重试，尚未执行项仍可接续。不得把收到任务 ID、请求返回或本地选择状态显示成全部正式入库成功。部分成功只适用于本节按项目选择入库，不能外推成整库覆盖或恢复可以半途成功。

验证：新请求逐项读回，项目数、关键值、关联和历史对账，再核对看板及导出。

建议删除先进入回收站；恢复重新校验引用和版本。完整数据库恢复与普通项目恢复分开，前者按运维流程执行，不开放为随手点击的业务按钮。

## SPEC-010 后台任务与重试

仅在确认任务需要异步时实施。任务状态：queued → running → succeeded / failed；失败可按策略重试，具体重试次数、超时及保留期限待任务类型确定。

收到任务 ID 仅表示已受理，不表示完成。状态接口必须给出任务类型、发起人、进度含义、结果和可用恢复动作。

若使用 Redis + BullMQ：提交与投递之间可恢复、任务执行幂等、产物写入有确定标识、进程崩溃可重试；同一任务不能重复改业务、重复生成被误认为不同的记录。重任务与交互请求分进程，限制并发。

未引入队列时不编写空的队列适配框架。需求明确后依据实测选型。

## SPEC-018 优先级与统一展示范围

状态：用户明确同意优先级沿用和展示范围统一（DEC-020/021）。

优先级：用户所说的紧急程度对应现有 priority，保留高/中/低，人工选择并点击保存。新建默认中，旧数据缺失或非法值的回退中须在迁移预检报告中可见。保留高优先级视觉强调、筛选统计与修改历史；灯色、交期、风险和阶段不自动改变优先级。服务器授权、事务及固定详情版本按 SPEC-002/014 执行。

## SPEC-019 公共业务设置与检查截止（截止范围已确认，剩余运维权限待决）

2026-09-30 用户修正：系统维护指定人员仅一个管理员账号；修改检查截止应直接应用本周。后续明确只选择每周星期几，截止日全天有效、次日 00:00 起逾期，保存后本周及以后每周沿用（DEC-046）。DEC-043/044/046 替代旧多人维护、固定下周生效和具体小时截止；共享资料改名/停用规则保持 SPEC-006 已确认行为。

### 唯一维护账号

公共企业信息、检查规则及账号启用/停用由唯一维护管理员明确保存，其他账号可查看公共业务信息但不可修改。用户确认额外创建专用维护管理员（DEC-045），即四个业务使用账号加一个维护账号；不占用四人业务账号。实际登录名与开通方式实施时确定。维护身份不自动取得项目负责关系。换任是将维护资格从旧账号原子替换到新的启用账号，不支持多人同时拥有此资格；换任不改项目负责关系、原审计或当前导入处理人。页面及直接请求均按服务器当前维护账号授权，不接受客户端自报管理员；自身停用限制按 SPEC-001；维护身份丢失按 DEC-054 受控恢复，实际运维操作者受控登记。

公共设置持久化服务器版本、保存人、服务器时间、旧值/新值及适用周；同一维护账号多标签页同样校验设置版本。企业信息契约见 SPEC-006。本入口不能调整已确定阶段顺序、进度比例、项目状态或负责关系。

### 本周截止立即应用

设置页只提供星期一至星期日的选择，不提供时分或任意日期输入。保存前展示原星期、新星期，并说明“本周立即生效，以后每周沿用”；本周对应日期可由系统作为辅助说明显示，用户无需填写。点击保存且事务提交成功后，服务器立即使用新截止日；新截止日已经结束时，本周未检查的应检项目显示检查逾期，新截止日在今天或以后时显示待检查。准确跨日边界见 SPEC-005。

已完成检查不因改截止变成未检查，不要求重复提交。当前周的按时/晚查标记以原检查服务器时间和本周新截止日重新计算；例如原周五改为周三，周三全天保存的记录仍按时，周四保存的记录仍为已检查但显示晚于新截止。反向延后截止也可能使原晚查显示按时，均注明当前采用的截止日和规则版本。检查人、时间、结论、备注和原记录依据不改写，也不创建虚构的新检查记录。

已结束自然周使用该周当时的有效规则，不因现在设置变更重算；已生成的报告快照保留当时采用的规则及截止日。查看“当前周最新判定”和查看“当时生成的报告”使用不同明确来源，不能冒充同一时点结果。规则变更保留追加历史，本周原截止不会无痕消失。

默认应检范围及截止日次日起才启动项目从下周要求仍按 SPEC-005；本周改截止不删除已有检查义务，也不凭设置修改追造原本没有的检查义务。首次应检周需依据实际开始时生效规则保留可复核依据，而不是每次用最新截止反推。星期选择只对应本自然周内的截止日，不接受将本周任务顺延到另一周的任意日期。

写入公共规则修订及审计同事务，失败保持原规则。提交后 SSE 通知检查摘要/数量重新查询，重连或页面聚焦时补查公共规则版本；旧页面不能一直按缓存截止判断。公共检查提醒刷新不替换固定详情业务内容，也不伪造项目 version 或进度更新。设置版本保护旧检查表单；在本周旧规则下尚未保存的检查，提示规则已更新并要求核对后明确保存，不自动提交。
