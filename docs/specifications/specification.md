版本：D0.60；日期：2026-10-09。当前范围以SPEC-001/DEC-090最小身份与完整E03为准，邀请码及完整账号后台后置；此前匿名范围保留历史标签，规则确认与实际实现分开，运行能力见系统真相及报告。

## 通用约定

- 尚未实现的写入/身份 API 路径为设计草案；实际已接入的只读接口以 api 目录及对应代码为准。
- 后续身份增强启用时，请求身份由服务端会话解析，客户端不能提交 actor_id 冒充操作人；当前范围按下节覆盖。
- 写请求只接受白名单字段，明确校验规则。服务端生成提交时间与新版本。
- 校验独立输入后再修改数据；失败不改变业务和审计状态。
- 返回统一错误码、可理解信息、request_id，保留用户输入。400 为输入结构错误，401 为未认证，403 为禁止操作，404 为对象不存在，409 为版本/业务冲突；暂定 422 表示业务字段校验失败。
- 文档中的“必须”用于规定目标实现，不表示今天已具备该能力。
- 首版规则取舍遵循 DEC-048：已确认契约优先；未改定的判断复用 V1.050；重大问题及人工无法纠正的问题优先核查修复。迁移必须增加的认证、授权、事务和版本保护仍实施，不自行新增业务自动推进、审批或完成门槛。旧流程证据见系统真相，新增业务选择仍需说明来源及影响。

首次使用临时密码认证后只允许完成改密及退出，服务端禁止访问业务接口、报告或 SSE。强制改密状态持久化于 MySQL，刷新、直接构造请求或重启不能绕过。改密成功后清除强制标志、撤销旧会话并重新认证，随后按账号权限使用；改密失败不清除标志。密码只能保存哈希。正式登录名变更保留账号 ID、负责关系和历史身份关联，不通过删号重建迁移人员身份。后续密码重置按下文 DEC-054 执行；重置不改账号 ID 和负责关系。

### 登录与可信身份细化（E02-F02 已确认，DEC-066；尚未实现）

本节输入处理、会话/防伪和反馈设计已获 DEC-066 确认；限速与哈希起始参数仍须实际测量，不据确认宣称已实现。施工步骤归 execution-plan，不另建可调用 API 说明。

- 登录名建议去除首尾空白并按 ASCII 转小写，最大 64 字符；注册名格式的详细限制留注册功能统一确定。密码原样比较，不截断、trim 或做 Unicode 归一化；建议长度按 Unicode 码点统计，拒绝空值和超过 128 个码点。登录不重跑“设置新密码至少 15 字符”的强度门槛；注册/改密才执行该门槛。HTTP JSON 请求体建议上限 8 KiB，先限制再做哈希。
- 所有认证失败（不存在、密码错误、停用）统一 401 和“登录信息不正确或账号不可用”；数据库不可用/审计故障是服务错误，不能伪装认证失败。限速返回 429 与等待时间，不能写 enabled=false 或要求维护人解锁。
- 登录成功是新会话与登录审计同事务提交；每次成功认证使用新的随机标识，数据库存会话/CSRF 摘要。密码验证后再在事务中检查账号启用、版本及密码哈希未变化，重置/停用先提交则不得沿旧验证结果开会话。
- 公网认证只通过 HTTPS；会话 Cookie 为 HttpOnly/Secure、Path=/、无 Domain，建议 SameSite=Lax。CSRF 随机值用同主机独立 Secure/SameSite Cookie 供页面读出，在写请求头提交并与该会话的 csrf_hash 比较；它不能单独用于认证。会话与 CSRF 原文均不进 Web Storage、草稿、日志或审计。本地 HTTP 仅有明确开发配置和独立 Cookie 名，公网配置不可降级。
- 登录/注册等未认证 JSON 入口也须验证配置允许的 Origin 及固定自定义请求头，拒绝跨站/来源缺失的浏览器写入；不开放跨域凭据 CORS。已登录写入口另核验会话绑定的 CSRF，不仅依赖 SameSite。
- 新请求身份查询只返回本人 ID/展示名、是否必须改密和当前维护资格等安全信息，Cache-Control=no-store；客户端身份/角色字段不能授权。临时密码身份只可取得本人最小身份、改密及退出；普通业务接口、他人资料、报告和 SSE 拒绝访问。
- 身份查询每次从 MySQL 核验会话撤销、账号启用和两种期限，不以跨请求身份缓存延迟停用生效。公共资料和项目权限由相应深模块核验，身份模块不预加载所有项目负责关系。核心写入在业务事务里再次保护当前身份/资格，不能把入口的一次读取当提交时仍有效的证明。
- 登录响应丢失时先用浏览器现有 Cookie 查询本人身份并核对与本次目标账号一致；不能把旧账号的身份查询成功当作本次登录成功。无有效新会话时才重新登录，登录不提供含秘密的持久回执；允许多设备，重复成功认证可能产生独立会话，未交付的会话按期限及受控清理处理。
- 页面启动确认身份后才请求业务数据；401 引导重新登录且停止旧账号的业务消费，503 显示服务暂不可用并保留当前编辑上下文，禁止把 503 当退出/草稿删除。账号切换清空旧身份的内存数据和通知连接，服务器个人状态按 user_id 隔离；原密码输入不自动持久保存。

限速与 Argon2 参数的工程起始值归执行文档。会话活动与到期精度按下文 F03 讨论段继续细化，不把旧 5 分钟节流建议当已确认规则。

### 邀请码注册细化（E02-F05 已确认，DEC-068；尚未实现）

复用多人同一码、固定 7 天、本人设置正式密码后正常登录及原子注册的已确认设计。下列字段格式、注册入口保护和反馈已获 DEC-068 确认，起始参数尚须实测；字段只归 ERD，方法只归执行文档。

- 注册页输入邀请码、登录名、展示名、密码与确认密码，明确点击“注册”。同浏览器已有登录身份时先提示当前身份，注册其他账号须先按 F03 明确退出；仍有有效会话时返回 409 AUTH_ALREADY_SIGNED_IN，注册接口不用于替换当前会话，不要求注册者已有维护身份。

- 登录名建议 3～64 个 ASCII 字符，首字符为英文字母或数字，其余允许字母、数字、点、下划线及连字符；去首尾空白并转小写，与 F02 同一规范化。展示名建议去首尾空白后为 1～128 个 Unicode 码点，允许中文且可重复，不允许控制字符；登录名全局唯一。资料选择用账号 ID，展示名重复时辅以登录名区分，不能把同名当同一人。
- 密码原样执行 SPEC-001 已确认的 15～128 码点规则，确认密码匹配；拒绝不完整 Unicode 输入，不 trim/归一化/截断。前后端均校验，注册失败可在当前表单修正，密码和邀请码不自动持久化。请求体沿用 F02 的大小边界；未认证入口沿用 Origin/自定义请求头、限速和有界哈希资源。
- 先低成本验证输入/邀请并可预检重名，再计算哈希；预检不是授权。事务以邀请码共享锁定读取取得最新记录，取锁之后再取服务器时间。只有 revoked_at 为空且检查时间严格早于 expires_at 才可创建；检查通过后的短事务正常提交可成立，不承诺物理提交瞬间仍早于到期。密码计算或等待锁跨过到期则拒绝，不能把点击时刻当授权时刻。
- 事务写入新账号、稳定 registration_invite_id 来源和脱敏注册审计；服务器决定 enabled=true、must_change_password=false、初始版本及时间。拒绝客户端提供 ID、维护资格、负责范围或这些系统状态；不自动关联旧工程师、已有项目、草稿或导入处理人。
- 同一有效邀请码、不同登录名可并发成功；规范化后的同一登录名仅一笔可提交，唯一约束最终保护。只有有效邀请通过后的重名检查/约束冲突提示“登录名已被使用”；不提供公开账号搜索/可用性探测接口，不用同名重试查找或改写现有密码。
- 注册与撤销共享同一邀请锁边界；注册先合法提交则账号保留，撤销先完成则拒绝注册。到期/撤销不回改旧账号状态，会话及停用规则按已确认契约。人数无固定配额，也没有邀请码使用次数字段。
- 成功响应只确认注册结果并引导正常登录，不自动开会话/强制改密；新连接对账为内部验收，浏览器不开放未登录账号读取接口。正常登录后取得可信身份并消费普通业务入口，自选加入项目后才能编辑，登录名或展示名都不能授予维护资格。
- 邀请不存在/格式不对/过期/撤销统一提示“邀请码不可用，请向维护人员获取有效邀请码”；输入错误 422，合法邀请码下重名 409，次数受限 429，服务不可用 503。已确认回滚的失败不留半个账号；结果未知提示先用本次登录名和本人密码正常登录确认，不能换登录名自动再建号。重复同名请求返回冲突，不以注册接口充当找回或覆盖。

注册速率起始值与锁故障重试方法归执行文档，设计已确认但参数尚未实测；不新增账号审核流程、自动维护权限或重复来源明细表。

### 会话与密码恢复（已确认，DEC-054）

允许本人多设备登录，各会话独立验证；本会话连续 7 天未有效使用，或距本次认证达到 30 天，均须重新登录。期限由服务器校验，届满边界即失效；SSE/自动轮询等后台保活不能让无人使用的会话无限延续。正常本人页面/接口操作记录 last_seen_at，写入节流见 ERD；浏览器缓存或其他设备活动不能绕过本会话到期。主动退出撤销当前会话，改密、密码重置或账号停用撤销该账号旧会话并使 SSE 失效。

业务账号忘记密码，由唯一维护账号明确执行重置：产生独立随机临时密码，持久设置强制改密、撤销旧会话并记审计；密码/哈希不进审计或日志，凭据受控交付。失败保持原凭据和会话状态，不显示成功。账号 ID、负责关系、项目数据及历史不随重置变化；使用临时密码认证后仍只可改密/退出，不能读业务。

唯一维护账号无法登录时，由具备服务器权限的操作者通过受控命令恢复登录凭据和必要维护身份，撤销旧会话并记录恢复操作。保持业务关联与历史，不创建公开找回接口、不借恢复转移项目责任。恢复执行环境及操作者登记在受控运维记录，不把凭据写入项目文档。

### 维护人员重置业务密码细化（E02-F06 已确认，DEC-069；尚未实现）

- 重置已提交但没有文件时，先核对当前结果窗口/本机已保存文件。确认原文丢失后，重新读取目标最新版本，说明原因，明确发起新操作；新临时密码替换旧密码，旧临时凭据及其产生的会话失效。不得因交付失败自动回退原密码、删号重建或从摘要还原明文。
- 启用中的目标用临时密码正常认证，只能查询本人最小身份、改密和退出；首次认证成功不清强制标志。本人 F03 保存正式密码后临时密码失效，旧受限会话也撤销，再正常登录恢复原业务范围。停用目标仍拒绝登录。原作者的未同步文字按 SPEC-007 保护，不转交给维护人员。

密码重置的目标选择、权限/版本/交付恢复及起始随机长度仍为本轮新增建议；回执及审计复用已有表，不建立临时密码历史库。

### 改密、退出与活动细化（E02-F03 已确认，DEC-067；尚未实现）

本节沿用 DEC-054 的改密撤销所有旧会话、退出仅撤销当前会话及期限，沿用 SPEC-007 的未同步草稿保护；随后展开的交互、恢复和活动精度已获 DEC-067 确认；性能与兼容性仍须实测。没有新增实体，使用 users/sessions/audit_log 及已有个人草稿。

- 本人改密输入当前密码、新密码与确认密码，明确点击保存；首次当前密码为临时密码，后续为本人正式密码。验证有效会话、来源/CSRF、当前密码及已确认新密码规则，建议拒绝新密码与当前密码相同。校验/验证错误不撤销原会话，不清强制标志；当前密码错误建议 422，不能用 401 误导页面退出。相关思路参考 [OWASP 改密建议](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)。
- 改密在同一短事务内重新核对账号快照和当前会话，更新 password_hash、清强制标志、推进账号 version、撤销该账号全部未撤销会话并写脱敏审计；失败整体不变。提交后清理当前浏览器认证 Cookie，提示用新密码重新登录，不沿用旧会话自动进入业务区。账号 ID、项目责任、正式项目及服务器草稿保留。普通用户主动改密前处理未同步草稿，首次受限改密不加载业务草稿。
- 改密响应丢失时停止自动重试密码提交，提示结果待确认，先由本人以新密码正常登录确认；401 只说明旧会话不可继续，不能单凭它证明改密成功。新密码认证失败可能还有后续重置/停用或服务故障，不能据此推断事务必然回滚。密码表单不进入草稿、日志、广播或持久回执，密码及其摘要不作为可查询的业务请求内容。
- 明确退出前按 SPEC-007 处理本浏览器当前账号未同步内容：保存底稿、复制/导出、明确放弃或取消退出；保存底稿不是正式保存项目。原样成功同步后或用户明确处理后才提交退出。需提醒同浏览器其他标签共享会话，不能静默丢弃其中未同步内容；未响应标签提示风险并由用户明确处理。
- 退出只撤销当前会话，写审计同事务；其他设备/浏览器会话保持有效。同浏览器共享该 Cookie 的标签一起退出。重复退出不追加重复撤销历史；数据库不可用或提交未知不显示“已退出”，实际会话核对/原范围重试后确认。已失效会话可清理本浏览器认证状态，但不作仍有效的身份执行其他写入。有效会话缺失 CSRF 时保持 F02 的拒绝规则，先同账号重新认证修复，再退出。
- 建议同浏览器同账号重新认证成功时，只撤销其携带的旧会话并交付新会话，不影响其他设备；换成不同账号先完成旧账号退出。认证提交、结果核对与 Cookie 处理在同源标签之间串行，不能让迟到退出响应清除刚建立的新会话。
- 有效活动是服务端已认证并接受的本人前台页面进入、搜索/筛选、操作请求，以及编辑产生的新输入活动；只读查看/搜索也可续本会话。无人操作的定时器、SSE/编辑在场心跳、自动刷新、身份轮询和自动重试不续期；仅放着页面不算持续活动。前台无网络请求的输入按执行文档的有界发送方式记录。客户端不能提交 last_seen_at 或历史时间补续期，断网期间未确认活动不计服务器有效使用。
- 活动先检查会话仍未到期/撤销，再以服务器当前时间单调更新该会话 last_seen_at；已过期不能靠活动请求复活，绝对到期不延长。建议每次确认的前台请求记录，不采用 5 分钟跨请求身份/活动缓存；静态资源和后台请求不写。活动元信息不推进账号/项目 version，不产生逐次业务审计。该精度和性能须实际验证；此前 ERD 的节流文字仅为候选，现改为引用本段。
- 账号切换前停旧请求/草稿队列与 SSE，确认退出并清本机旧账号敏感缓存，登录新账号后重新取得身份，再恢复新账号自己的状态。每个已认证业务请求建议带页面进入时的 expectedAccountId，服务端必须先解析真实会话，再检查一致；该 ID 只阻止错误上下文，不能授予身份/权限。不一致返回 409 AUTH_CONTEXT_CHANGED，不读写业务。SSE/下载不能设置请求头时使用非秘密的同等上下文参数；会话/CSRF 不放 URL。
- 前端请求与页面数据绑定身份代次，旧请求的迟到结果不能填回新账号页面；同源标签通知只传身份变更类型，不传密码、会话或草稿。异常失效时旧未同步文字先隔离并停止写入，同一账号重新认证再恢复；换到另一账号之前仍须处理旧输入，不把它转存给新账号。具体草稿恢复规则仅归 SPEC-007。
- 撤销提交后主动关闭相关旧通知连接；发送新事件前及重连时重新检查会话，漏掉主动关闭也不能继续送受保护事件。实际退出/撤销及物理连接关闭分开验证，SSE 未实现时只验身份边界，不能称通知链路已经通过。

### 账号停用与交接（已确认前置，DEC-038）

用户选择先完成项目交接才允许停用。账号启用/停用及唯一维护账号变更由唯一维护管理员管理（DEC-043，替代 DEC-040 的多人维护范围）；交接完成标准已由 DEC-041 确认：该账号当前负责的每一个项目（含结案项目）都已有至少一位其他启用中的负责人加入并保存。没有负责项目时该项前置自然满足；已停用账号不计为可用接续人，不能把“停用后再认领”实施为默认。后端按当时负责关系及启用状态验证，缺少接续人时列出阻塞项目并拒绝停用；不要求先删除原负责记录。

工程保护：不能停用本人或最后一个有效账号；后端校验当前账号状态及版本，并发操作也不能留下全部停用的结果。停用与业务审计、会话撤销同事务；保存成功后该账号不能新登录，既有会话及 SSE 失效，后续读写重新校验启用状态。已在停用前提交的数据保留，不通过停用倒撤其合法历史；停用与写入竞态必须形成可验证的一致提交次序。

停用不删除账号、审计、项目资料或原负责关系；名单显示已停用，项目当前阶段、计划、灯色及检查记录不变。停用提交前重新确认全部项目接续资格，并与负责关系变更、相关账号停用形成一致事务次序，避免检查后接续人退出/停用仍提交；不自动随机分配；停用后的正式负责关系及最后退出前置仍按 SPEC-014 执行。该提示不是项目生命周期状态，最后负责人主动退出前置仍按 SPEC-014 执行。重新启用账号的资格和明确保存需遵守同等维护权限，原已撤销会话不能复活；原负责关系如仍存在可恢复其编辑资格，历史期间操作不撤销。

不能从本节推导看见他人密码、无痕改历史或批量替别人加入/退出。密码恢复按 DEC-054；用户增补现已通过上文邀请码机制确认；停用后的基础资料归属和账号删除不据此扩展。未完成导入批次的明确接管见 SPEC-009 已确认规则。

接口草案：`POST /api/auth/login`、`POST /api/auth/logout`、`GET /api/me`。未认证请求不得读取业务数据和报告下载。

## SPEC-002 保存、事务、并发与审计

### 明确保存

用户确认：普通文字、信号灯、优先级、阶段、结案等一切业务信息修改，都必须点击“保存”后提交。选择、输入、拖动、失焦、切页、计时或接收通知不能自动提交；新增/删除子记录、节点位置和关联变更也属于修改。操作表单中可显示“保存阶段变更”“保存结案”等明确文案，不能仅点选状态就生效。取消不改变正式数据。

输入：业务动作参数、进入详情时取得的 expectedVersion；创建及可重复副作用动作携带幂等键。权限依据 SPEC-014。

处理：验证身份与输入 → 在短事务内核验当前项目负责关系及版本 → 按 ID 与版本条件更新 → 写业务子表和审计 → 提交 → 返回已保存数据与新版本。负责关系变更与业务写入采用同一项目并发边界，避免“检查有权后权限被撤销仍提交”的竞态。更新行数不满足预期时回滚并返回冲突，不静默覆盖。

幂等键按用户和操作范围约束；同键同请求返回原结果，同键不同内容返回冲突。幂等结果与业务提交的一致性必须有测试。

失败：数据库或审计失败时回滚；响应丢失后通过幂等结果确认是否已经提交。版本冲突返回 409，提示“项目已被他人更新，请重新进入项目”，不得把旧输入换一个新版本号继续提交，不自动合并或强制覆盖。用户已确认：保留未保存文字供复制，禁用旧版本保存；点击重新进入前提醒未保存内容不会自动带入新版本。

接口草案：`PATCH /api/projects/{id}` 仅更新普通字段；生命周期变化通过专用动作。项目级 version 统一保护子对象写入，初期接受较粗的冲突范围。

### 进入详情后的固定版本

1. 进入项目时获取同一已提交版本的项目数据、子记录与版本号。技术实现以短事务/一致性读取取得完整视图，不为用户停留页面而长期保持数据库事务或锁。
2. 页面显示进入时的数据；其他人的编辑内容不广播，其他人的保存结果也不自动替换此详情。只读进入同样遵循固定视图。
3. 发现项目版本已变化时，显示上述提示并使旧页面不能保存；用户点击重新进入，重新读取最新数据及权限。不要求先显示字段差异。
4. SSE 未送达时，重连、页面聚焦及保存前的服务端校验仍能发现变化。无法确认服务端状态时不得显示保存成功。
5. 同版本的两个并发提交只允许一个成功；不同字段、同账号不同标签页的旧版本提交也不能绕过校验。
6. 本页自己的保存成功后，以服务端返回数据和新版本建立下一次编辑基线；通知带本次提交标识，避免把自己的成功保存误报为他人更新。
7. 看板列表可刷新摘要；已打开详情仍保持其版本并提示过期。在线编辑名单独立刷新，不改变业务数据版本。

个人页面位置等浏览偏好与业务修改区分；它们的自动恢复不构成业务保存。服务器个人草稿按 DEC-052 自动持久化，行为见 SPEC-007；公共业务设置仍需明确保存，个人显示配置可自动记录。

### 项目详情的保存粒度（已确认，DEC-053）

普通字段、资料选择、业务人员、普通说明、计划参数和正在编辑的子记录统一进入本页编辑副本，点击“保存项目”提交同一聚合变更。子记录弹窗的“确认添加/修改”只更新编辑副本，页面持续显示“项目尚未保存”；删除子记录、改连线或拖动业务节点位置也纳入该副本。服务端接收明确变更集合，而不是覆盖客户端未加载的集合；普通保存拒绝夹带项目生命周期、阶段实际状态或负责关系变更。任一关联或审计失败整体回滚，所有本次普通改动均保持未保存。

开始/完成阶段、纠错、回退、暂缓/恢复、结案/重开、负责范围及明确检查等使用各自操作表单和“保存该操作”按钮，同样受项目统一版本保护。普通编辑尚未保存时先提供“保存项目后继续”“明确放弃普通编辑后继续”“取消本次动作”；保存失败不继续状态动作，不把未保存普通字段暗中夹进动作。先保存普通编辑会取得新版本，再基于该版本重新检查状态动作前置。项目以外页面的独立业务表单仍明确保存，并使用其所属实体版本。

自己的保存成功后更新本页基线；其他页面实例和其他草稿即使同账号，也不能自动换版本继续写入。草稿清理及迟到同步见 SPEC-007；本次收敛不改变他人更新时保留文字、重新进入的既定规则。

### 当前测试项目四项编辑与临时恢复（已确认，DEC-077）

本段仅适用于当前免登录测试范围。后续身份下的服务器私人草稿继续按 SPEC-007；本标签页临时副本不提供账号隔离或跨设备恢复。

1. 新 GET 取得有效详情、进入版本及服务端能力后才能编辑四项；首次读取失败提供重试/返回，没有有效结果不能保存。项目名称单行，三项说明多行；沿用原字段，不另建项目备注/汇总备注同义字段。名称不能仅含空白，容量按 ERD，说明允许明确空字符串清空；遗漏表示不修改，保留原文及换行，不自动截断文字。
2. 进入快照与编辑副本分开；切页签保留输入。与基线逐字段比较，全部恢复原值时无变化、保存不可用。过期标记独立于是否有修改，改回原值不能解除过期。
3. 点击保存先校验并聚焦错误字段；合法时固定本次变化、操作编号及进入版本，发出前保留恢复信息。保存中冻结四项输入、重复提交、放弃及重新进入，允许查看只读页签和复制文字。明确失败解除冻结并保留副本；结果未知保留原请求，停止新提交，提供确认结果及复制入口。
4. 确认成功用本次提交结果建立基线，清理准确对应的副本；后续读取独立执行。已发现更高版本时，迟到的旧成功响应不能清除过期提示。版本冲突保留旧快照及文字，只供复制核对，重新进入前提醒处理未保存输入；新 GET 失败保留原内容。
5. 临时副本使用 sessionStorage，仅存本测试项目四项输入、原基线版本与必要待确认请求，按项目和结构版本区分。输入先在内存更新，短暂停顿合并写入，切页签、保存及应用内离开时尽力补写；不逐按键同步序列化长文本。存储失败继续编辑，提示仅内存保留并提供复制；内容不写 URL、日志，清理只针对匹配副本，不全局 clear。
6. 刷新后先 GET 核验正式版本和能力，再读候选副本；存在待确认操作时优先沿原编号确认结果。基线相同且可编辑时由用户选择恢复，基线过期时只供复制，不能替换副本版本强行提交。复制标签页可能继承候选副本，它不代表身份或独占权限，重复待确认请求仍受数据库回执保护。
7. 应用内离开时，有未保存输入提供保留本标签页副本并离开、继续编辑、明确放弃。结果未知时只能保留原操作恢复信息并离开或取消离开；放弃输入不表示撤销可能已提交的操作。浏览器刷新/关闭提醒仅为辅助，最后输入及异常关闭不保证恢复，也不在 unload 自动正式保存。
8. 旧 GET、迟到保存响应不能覆盖新的基线或输入，较低版本不能清除已发现的较高版本。通知接入前，聚焦/重新进入的补查只标记过期，保存端仍校验版本，不自动替换输入。

### 当前保存与恢复附则（授权代决 DEC-080～082；未实现）

- 当前四项请求绑定项目、进入版本、稳定操作编号及精确变化集合；只有服务端核验为 trial 才可匿名写入。省略不修改，空字符串按字段规则清空，越界字段应明确拒绝而不是过滤后默默保存。
- 项目锁与当前回执读取在一个短写事务中；原回执对账优先于新操作版本检查。同范围同编号同请求返回原结果，同编号不同内容拒绝。原回执只证明原动作，返回原保存版本/值，即使当前项目已更高也不能改写。
- 新操作必须先匹配版本，再比较数据库旧值。有实际差异时项目推进一次版本，并将业务、准确审计和回执同事务提交；无实际差异时版本/业务历史不变，同事务保存 changed=false 的回执。无变化结果 savedAt=null，有变更时间由服务器产生。
- 确认 COMMIT 后返回固定本次结果；HTTP 当前 request_id 与原回执业务结果分开。已确认未提交的输入/范围/版本错误和回滚可以修正后新建操作；提交结果未确认只能保留原编号/固定内容对账或重试。操作编号复用冲突不能盲目换号重复待确认动作。
- 确认结果入口以原固定请求对账，使用相同摘要计算，核验项目范围；它只读，不创建回执或推进项目版本。查到匹配回执才确认原结果；未查到、读取失败或项目不可读均不证明原提交未发生。同请求原编号重试受相同事务和唯一约束保护。
- 保存已确认后再读取当前详情/看板/历史；新读失败只报告刷新失败，不撤销成功事实。新读版本更高则保持固定详情规则并提示重新进入，较旧响应不能覆盖较新已观察版本。
- 新审计按项目读取，有界游标分页（默认 20、最大 100，工程参数 DEC-086），不塞进每次列表/详情完整载荷；该上限是单次读取条数，不是项目历史总量限制。audit_log 与 legacy_project_history 分开展示来源、时间语义及记录，旧历史不改写；正文以文本安全渲染，空白/换行和 emoji 不丢失，只有有实际变化的动作显示修改前后字段。

具体请求/响应错误码与代码落位归执行文档 W02～W04，实际协议在实现后记录 api/；本附则不声称已经通过运行测试。

#### 新建、S1 与正式启动

沿用“先做 S1 需求立项，再进入正式执行”的业务顺序，但将自动改变项目状态改为明确人工启动：

1. 新建保存后为提案中，S1 待开始，其余阶段未解锁；录入账号自动负责。名称必填，客户等资料允许逐步补齐，真实新建不借状态下拉直接指定已结案或已完成阶段。
2. 提案中允许负责人开始 S1、完成 S1，均需明确保存；完成后 S1 已完成、S2 待开始，项目仍提案中。此时 S2 显示“需先启动项目”，不能开始；阶段前置满足不等于项目已获准执行。
3. 负责人选择“启动项目”，核对项目实际启动日期、预计结案日期及项目名称，点击保存后改为进行中。S1 须已完成；启动日期可补录过去真实日期，不能早于 S1 实际完成日期，未知历史数据走迁移核对；预计结案日期不能早于实际启动日期。客户等其他字段不新增强制门槛，至少一位负责人由当前操作权限保证。
4. 启动项目不自动开始 S2；负责人再按 B 开始 S2 并保存。项目启动日期与 S2 开始日期分别记录，允许先确定正式执行、稍后实际开工。
5. 已进行中的项目因返工回退至 S1 时，项目总体仍进行中，S1 待开始；不自动变回提案或重写首次项目启动日期。新建初始化与后续返工不能混为一条规则。

“启动项目”是已确认的独立人工动作；旧代码 S1 自动改项目状态的行为不沿用，源码事实见系统真相。

#### 暂缓与恢复

提案中/进行中都可暂缓，保存原因并记录此前项目状态；阶段状态、阶段日期、进度和已有成果保留，页面明确显示项目暂缓，不把保留的阶段进行中当成仍在执行。

暂缓期间允许保存文字、计划、说明、灯色、紧急程度及事实纠错，继续遵守权限、版本和日期顺序；不允许正式启动、开始阶段、完成阶段或真实返工回退。纠错用于修正既有事实，不能借普通字段修改把项目恢复或代替新的推进动作；本节不要求判断用户业务说明的真实性。

负责人保存“恢复”后回到暂缓前的项目状态，阶段继续使用保存的状态：原来进行中的仍进行中，原来待开始的仍待开始，不额外生成阶段开始记录。恢复前展示计划供核对；改期必须明确修改并保存。

恢复使用暂停期间最新已保存的阶段和项目信息，不把暂停前整份数据覆盖回来；事实纠错、文字或计划的合法保存继续有效。暂缓原因及恢复说明的文字纠正沿事实纠错约定，保留原文、原操作人/时间，以新增更正及理由表达；暂缓原因更正后仍须非空，选填恢复说明允许明确清空。更正说明不改变总体状态、实际日期或阶段，不代替恢复动作。

暂停不自动顺延计划、不扣除日历天数；暂缓标签单独展示。完整逾期公式、参与状态和时区见已确认 SPEC-004。

#### 结案、量产维护与重新打开

保留项目状态“已结案”，结案表单由人选择“正常完成”或“中途终止”，必填结案说明并确认实际结案日期，允许符合真实情况的历史补录，服务器另记操作时间。显示未完阶段、节点和未关闭风险供核对；有遗留事项时填写其处置说明，不静默删除或标为完成。

新建项目的结案日期一致性按DEC-096：实际结案日不得晚于服务器业务今天，也不得早于已知的项目实际启动日及当前有效阶段的实际开始/完成日；同一天允许。未知日期不补造，不要求七阶段完成。有已知错误日期时先走事实纠错，不能自动推迟结案日或把阶段标为完成。

导入已经完结的项目是历史事实入库，沿SPEC-009审查保留“已结案”、原实际结案日和原有效阶段事实，不重新执行启动、阶段完成或结案动作。导入保存时间只表示本次入库，不代替过去实际结案日；缺失实际日期、结案类型或结案前状态保持未知并显示核对提示，不因不满足新动作表单而虚构历史。已知日期矛盾须在卡片中逐项列出，是否必须纠正后才能正式入库仍待Q-025，不能将本次新项目校验默认为旧数据全表门槛。

系统不根据所有节点完成、红黄绿或阶段数量自动结案，也不要求七阶段全部完成才可提交结案。负责人对实际交付结果作判断，系统负责输入及一致性检查。因此实际阶段进度可能低于 100% 而项目已结案；正常完成与中途终止在统计中应能区分，阶段进度不能当作结案率。

结案后保留真实阶段状态和进度，以项目已结案状态禁止新阶段开始/完成/真实回退。允许负责人补充说明和纠正文字、日期等事实；涉及有效阶段状态变化时先走重新打开，不能直接改总体状态绕过记录。正常结案与中途终止不自动打开量产维护。

旧模型的 S7“MP量产维护”是阶段名称，“已结案后的量产维护”是另一个标识。首版保留两者：前者记录阶段工作，后者用于结案后的持续支持；开启维护不重开项目或重置阶段，操作范围另按节点/风险规则确认，不能因此开放研发阶段推进。

重新打开由负责人填写原因并保存，恢复结案前的项目状态和当时阶段状态（包括原暂缓情况），关闭仅对已结案有效的维护标识并保留历史。若目的是回到较早阶段重做，再按已确认回退操作选目标，保存后待开始；原结案记录不抹除。结案前全部阶段已完成时，重新打开不凭空启动阶段，需要明确回退目标。不得把重新打开等同于自动开工。

闭案期间合法保存的文字、计划和日期纠正继续有效；重开保持当前已保存的阶段事实，不用当时整项目快照覆盖纠正。恢复依据必须可靠，不能凭阶段进度猜结案前状态；历史导入缺失依据时指出待核对项。重新打开后的周检查按SPEC-005当前总体状态和原首次义务判断，不重建首次义务、不生成检查；原暂缓项目仍先恢复暂缓，不能直接计入进行中。

| 情况 | 确认处理 | 后续阶段与日期 |
|---|---|---|
| 文字、计划或实际日期填错 | 修改指定信息，保留阶段状态 | 实际日期违反顺序时指出冲突，不静默移动其他阶段日期；计划变更不推导实际开始 |
| 当前阶段误点开始，尚未完成 | 撤销开始，回到待开始 | 清空本阶段当前有效实际开始日期；旧值留审计；后续保持未解锁 |
| 当前阶段误点完成，下一阶段尚未开始 | 撤销完成，回到进行中 | 保留本阶段有效开始日期，清空有效完成日期；下一阶段从待开始回到未解锁 |

目标阶段若连开始记录也是误填，可在同一纠错预览中明确选择回到“待开始”，同时清空其当前有效开始/完成日期，后续均未解锁；不能只取消完成而保留错误的开始。旧数据缺失可靠开始信息时报告待核对，不能凭回退动作补造时间。

全部变动必须在同一次保存后构成合法串行状态。预览期间其他人保存导致版本变化时拒绝整次纠错，不能使用旧预览覆盖最新项目。

#### 保留内容与联动范围

节点、阶段评述、已有成果、风险与变更记录均保留，包括原来的节点完成记录。撤销阶段不等于这些记录也填错；若其中某条记录本身错误，应单独纠正。页面须区分保留的历史记录与当前阶段状态，历史评述不能自动作为下一次完成的确认说明。

计划日期保留，不因回退自动整体顺延。红黄绿、紧急程度和项目负责关系保持原值；项目总体状态不由阶段纠错隐式切换。已结案项目重开、暂缓时的操作限制见上文已确认项目状态联动，不能通过阶段纠错绕过。

保存后自动更新当前阶段展示、后续解锁资格及按已确认算法派生的进度；下一次开始仍按 B 另行保存。审计记录操作人、服务器保存时间、纠错理由及全部旧值/新值。看板与新请求使用保存结果；其他已打开详情按固定版本机制提示过期。

#### 实际日期规则

- 正常开始/完成表单默认当天，可在保存前改成真实发生的过去日期；只填写日期不产生状态转换。未来日期只用于计划。
- 业务实际日期按天记录；服务器另记精确的操作时间，补录不能修改审计时间。
- 同一阶段开始日期不得晚于完成日期；后阶段开始日期不得早于前阶段完成日期。同一天完成和开始允许，不要求相隔一天。
- 按DEC-092，S2及后续阶段不另加“实际开始日期不得早于项目实际启动日期”的校验；项目启动与阶段实际发生日期分别记录。正常操作仍须先完成项目正式启动，阶段日期仍维护同阶段与相邻阶段顺序，且不得填写未来实际日期。启动项目自身不得早于S1实际完成日的前置保持不变。
- 修改较早阶段日期造成与后续冲突时，展示冲突并拒绝该次保存，用户先核对真实日期；系统不自动挪动其他阶段日期。需要同时改多个日期时在同一预览与保存中校验完整结果。
- 缺失的历史日期保留未知，不把导入日或首次访问日当作实际日期；历史补录与普通推进的校验范围在迁移映射时明确。

#### 实际日期明确纠正为未知（已确认，DEC-108）

原面板阶段日期编辑直接写表单值，日期可空而完成标记仍在。目标提供明确事实纠错：项目提案/立案/实际启动/当前有效结案日期，以及阶段实际开始/完成日期，若已录值有误且真实日期暂未知，当前负责人选择“纠正为日期未知”、填写原因、预览旧值与受影响结果后明确保存；仅将选定日期置NULL，原日期及每次纠错保留审计。普通空白、省略和文字编辑不能执行此意图。

确实发生的项目启动、阶段开始/完成、结案状态及类型保持；阶段进度仍依据有效完成状态，服务器原操作时间、首次周检查依据不重写。动作本身没有发生时使用对应撤销/重新打开等已确认入口，不能把日期清空冒充动作撤销。节点仍沿SPEC-005用实际完成日表达完成，清空节点完成日表示未完成，不套用本条。

未知日期不参与已知日期大小比较、不转换为今天/0；本次明确未知纠错可保存为待核对事实，不能因其选定清空的日期未知就封死纠错。候选中仍已知的相关日期保持既有顺序约束。后续开始/完成/启动/结案等动作若必须使用某个未知日期校验，指出具体缺失字段和补录入口，核对后再保存该动作；无关文字/计划修改不增加未知日期门槛。仍已知日期的更正及共同多日期纠错继续校验最终结果。

当前有效结案日未知时仍显示已结案，日期结果按SPEC-004显示待核对。保存沿SPEC-002/014的身份、责任、版本、事务和未知结果恢复；日期事实与审计/回执同成，失败保留输入，不先清空一部分。不扩展到跨结案周期历史日期更正或Q-025导入已知矛盾的入库门槛。

#### 周期、截止与适用范围

服务器判定按实际保存时间是否早于“截止日次日 00:00”的排他上界执行，不将最后时刻写死为 23:59:59，避免丢掉秒以下精度。实际 checked_at 仍记录服务器时间点，截止精度按天不改变审计精度。选择周日时上界恰为下一周一 00:00，届时进入新自然周，旧周记录保留；新周提交不归入旧周。

默认每周必查范围为进行中项目；提案和暂缓允许主动检查，但不纳入默认每周必查数量。按DEC-100，已结案也允许负责人主动保存检查，不要求新周例行检查，历史保留；主动检查不重开项目或改变维护/阶段，也不建立首次义务。历史账号和记录缺失不能伪造检查人/结论，旧lastCheckAt保留来源，不直接升级成可信的新检查记录。

首次应检周及所用规则修订与启动结果同事务保存，之后改截止不重新计算首次义务；补录或纠正业务启动日期也不单独改变这项保存依据。当前周及历史的截止变化仍按SPEC-019处理；启动保存不代表已检查，不生成项目检查记录。已导入历史项目缺少首次义务依据时保留未知并核对，不把导入日或访问日冒充首次启动保存日。

暂缓/恢复都不创建检查、不重置首次应检周/原始规则，也不为暂缓各周追造漏检或检查事实。恢复只影响当前查询的应检范围；已有历史记录和固定报告不因恢复重写。缺失首次义务依据的历史项目继续走核对，不能用恢复时间伪装成首次正式启动保存。

检查逾期只是检查动作超过截止，不能当作项目交期超期。隐藏 CHECK 显示是个人页面偏好，不能删除检查记录或把未检查改为已检查。检查周期/截止作为共同业务设置统一由服务器保存，权限与生效规则见 SPEC-019；调整规则不能重写已经记录的检查时间。

### 草稿自动同步、失败与多窗口

编辑停顿 1 秒后同步草稿，持续输入时最长每 5 秒同步一次；按同一草稿串行发请求并保存客户端序号，服务器校验独立 draft_version，迟到请求不能覆盖较新草稿。输入先保留于当前内存和按账号隔离的本地故障副本；收到服务器持久化确认才显示“草稿已同步”，该提示与“项目已保存”始终分开。云同步失败不阻塞继续输入或正式保存；提示“草稿未同步，仅保留在当前设备”，提供复制/导出入口。

每个新编辑页面生成独立页面实例及 client_draft_id；刷新通过原实例上下文恢复。新标签页、复制标签页、另一设备均不默认共享一个草稿写入权；恢复已有草稿继续编辑时生成新的草稿副本，保留原稿供核对。本账号的多个草稿可并存，其他账号不得查询其内容；同草稿发生并发修订时拒绝旧草稿版本，保留本页输入并提示重新读取或保存为另一份草稿，不静默合并。

收到项目过期提示后禁用正式提交；本人旧基线草稿仍可同步其输入以保护文字，服务器不得据草稿写入改变旧项目。本人已退出负责范围或账号失效时不再接收该项目新草稿写入；仍启用的原作者可读取自己已有草稿作复制，正式写入必须重新加入并读取最新版。会话过期时本设备保留未同步内容，同一账号重新登录、核验权限后只允许继续同步本人草稿，不自动提交项目；换账号不得恢复前一账号输入。

### 正式保存、离开及清理

正式请求包含本次提交的内容及明确的草稿标识/修订。成功事务只把确实对应本次提交的草稿修订标记 committed；若该稿已有后续输入，保留后续稿，不清除其他标签页或其他账号的草稿。已 committed/discarded 的稿拒绝迟到自动写入，继续新编辑另建草稿。响应丢失先按提交回执查询，不因页面仍有草稿就重复创建项目。

离页/刷新时有未提交内容，应用内导航提供“保留草稿并离开”“继续编辑”“明确丢弃”；草稿未同步时强调仅当前设备可恢复，并可复制/导出。浏览器强制关闭无法保证最后一次网络同步完成，恢复时同时核对本机故障副本和服务器已确认修订，不宣称零丢字。

退出或换账号清理本机敏感缓存；退出前有未同步内容则提供保存底稿、复制或明确放弃入口。服务器草稿不会随退出删除。账号停用不把草稿交给其他人，完整备份包含其持久草稿。

保留与容量（已确认，DEC-055）：未提交 active 草稿不自动过期；用户明确丢弃或对应正式保存后才标记终态。单份 payload_json 的规范 UTF-8 序列化有效载荷上限为 1 MiB（1,048,576 字节），每账号最多 100 份 active 草稿；所有设备合计，更新现有草稿不新增计数。创建/恢复新副本需原子校验名额，跨设备并发不得超额。

超限拒绝本次云同步并显示原因，保留服务器已有稿和本机当前输入，提供清理/复制/导出入口；不自动删旧稿、不截断输入、不把同步失败显示为成功。普通正式保存仍按业务输入限制处理，不能因为草稿同步失败就悄悄提交。已提交/已丢弃稿的自动清理期限和回收站规则仍待 Q-017，暂不启动该类清理。

验证：真实草稿写入后用新会话读回；断网/重启/换账号/多窗口/迟到请求/项目过期/权限撤销/正式保存并发均按本节检查，特别证明自动底稿不会产生正式业务提交。

底稿与个人状态 JSON 都带明确 schemaVersion，按表单/白名单 scope 校验。底稿只承载本人可编辑输入与子记录变更；新子记录用客户端临时键关联，正式保存由服务器生成 ID 并返回映射，不把临时键写成 SQL 外键。更新客户端遇不支持的旧底稿结构时保留复制/导出入口并提示重新核对，不能截断、静默丢字段或自动改成正式业务。具体 JSON 契约随实际 API 产生，归 api 目录并注明代码/结构版本。

## SPEC-008 会议、统计与报告

报告输入包含项目范围、字段、筛选、报告名称及格式。建议固定生成时快照，记录生成账号和时间；导出读取相同快照，避免过程中读取多个不同版本。

多行状态、人员、芯片、维护标识、项目备注等按选择输出。HTML/Markdown/CSV 各自正确转义，CSV 需评估公式注入处理且不破坏业务原文。下载结果可追溯并受认证保护。

会议开始、暂停、继续、结束均是业务动作；计时依据保存的时间点，浏览器关闭不丢会议。会议与报告的最终数据结构仍需 Q-012 确认。

结果必须可下载或供下一步汇报消费。任务状态成功但产物无法下载不算完成。

输入：旧 JSON 原文件、明确来源、备份 schema 版本和冲突策略。

预检：容器结构、语义 ID 重复、名称引用、非法阶段、缺失日期、旧字段及业务备注；输出逐项映射和未解决项。无预检确认不得执行覆盖导入。

### 独立卡片审查区（已确认范围，DEC-032）

2026-09-30 用户要求独立入口、卡片审查、有误才修正、正确项选中后批量审查，并明确选择“先进入审查区，确认后写入正式数据”。上传和预检只生成待审数据，不改变正式项目、看板、统计、正式项目历史或每周检查记录。结构预检通过不等于人工已审查。

独立“批量导入审查”入口按导入批次恢复待办。卡片可查看导入内容、预检问题及拟新增/更新的结果；已有项目同时呈现正式值和导入值，避免只看新值无法发现覆盖。以项目及其关联资料作为主要卡片粒度是界面建议，独立基础资料的展示方式在完整字段反推后收敛。

- 有误：进入待审内容纠正，点击“保存待审修正”后仍留在审查区；正式项目不受影响。已选中的内容发生修改时取消该项选择，核对最新内容后再选中。
- 正确：勾选卡片；勾选本身不写正式数据，不自动完成审查。点击“保存所选审查（数量）”前显示拟新增/更新对象、关联影响及未解决问题；明确保存才提交选中项。
- 未选项继续待审，可以分次处理；不能因为一批里大多数正确就自动通过其余卡片。已提交项显示实际结果、正式对象链接、审查人和服务器时间，重试不能重复新增。
- 待审区及其修正、选择和提交结果保存在 MySQL，可在重新登录或应用重启后恢复；纳入 SPEC-016 的全部持久数据备份。正式入库前仍须重新校验已确认业务规则、引用、身份与权限。

审查导入资料表示批准本次导入内容，不等于完成 SPEC-005 的每周检查；入库后项目的检查动作仍须另行确认并保存。系统只自动提示格式、引用、阶段/日期约束和版本冲突，不替人判断风险已经解除、阶段应该完成或项目应该结案。

已完结旧项目与新项目结案动作的区别按SPEC-003/DEC-096；审查映射保留原结案事实，未知与已知矛盾分别列出，已知矛盾入库门槛仍待Q-025。不能用新动作的必填表单规则静默重演旧项目生命周期。

### 待审内容的协作权限（已确认，DEC-035）

2026-09-30 用户选择“首次入库卡片只由上传者纠正和提交”。四人均可查看所有导入批次及逐项结果；首次入库项目的待审卡片默认仅该批次上传者可纠正和提交；经 DEC-039 明确接管后由当前处理人处理，其他账号只读，不能通过直接请求绕过。上传者来自服务端可信账号及持久批次记录，不根据文件内的创建人、工程师或本地模式判断。

更新已有正式项目的待审卡片仅该项目当前负责人可纠正和提交，上传者身份不另行授予修改权；非负责人可以查看，需要处理时先自行加入负责范围、保存并重新核对。所有写入端重新判定待审项属于首次入库还是已有项目更新，不能信任客户端声明类型。账号/共享资料维护及公共设置权限见 SPEC-001/006/019；数据库恢复与备份维护权限仍待 Q-016 对应运维问题，不由待审权限推导。

卡片纠正须明确保存，服务器校验 review_version。相同账号不同标签页，或有权负责人同时打开相同待审版本，A 保存修正后 B 保留旧输入供复制并提示待审内容已更新；B 不能保存旧版本或提交旧选择，重新进入核对。提交既检查待审版本，也检查目标项目版本与当时负责关系。相同待审项并发提交只能得到一个正式结果，其他请求读回已经提交的结果，不重复新增。

上传者、修正者、审查提交者分别记录可信账号及服务器时间；首次入库在此权限方案下由上传者提交，但仍保存各动作来源，不将上传文件当作原项目创建事实。共享待审内容与本人选中集合区分，不能用另一人的选择冒充本人确认。原上传者不被改写，停用后的明确接管见 DEC-039；不能自动接管。

### 停用处理人后的批次接管（已确认，DEC-039）

用户明确允许填写原因、保存接管并保留历史。首次入库待审项默认由上传者处理（DEC-035）；当前处理人初始等于上传者。只有当前处理账号停用后，其他有效管理员才可查看剩余项、填写原因并点击“保存接管”；处理账号仍启用时不能任意夺取批次。

接管后单独保存当前处理人；原上传者及历次处理人保留来源和追加审计，不重写创建事实。仅当前处理人可纠正和提交未完成的首次入库卡片；原上传者重新启用后不会自动拿回已接管批次。若后续当前处理人也停用，下一次明确接管采用同样前置与历史记录。

接管不直接通过卡片、不入库、不改已提交项目的负责关系；更新已有正式项目的卡片仍按项目负责范围。接管者重新进入、核对最新版后再修正/选择/提交；旧页面及旧选择不能继续提交。新入库负责关系仍属于实际保存入库者（SPEC-014），不能因接管批次就负责之前成功的项目。

批次版本保护并发接管；校验当前处理账号停用、改当前处理人、推进批次权限版本及写审计同事务，并发只允许一个结果。接管与项目提交形成明确先后，读取各项实际结果，不重复入库或遗失成功项；应用重启可回读当前处理人及剩余项。处理资格与待审内容、目标项目版本均需在提交时重新校验，SSE 仅提示变化，不替代服务器授权。


### 并发、引用及待决边界

准备更新已有项目的卡片固定对应的正式项目版本；审查期间他人保存后提示“项目已被他人更新，请重新核对导入信息”，保留待审修正供核对，禁止以旧版本入库。重新读取正式项目并核对合并结果后才可再次提交；即使 SSE 遗漏，提交端也必须校验版本。更新已有项目仍受 SPEC-014 负责范围约束，不能以批量入口绕过授权。首次入库负责及旧来源保留见 SPEC-014 已确认规则，不能自动从旧 PM/工程师授予账号权限。

选中项目依赖的客户、芯片等基础资料必须有明确映射和提交范围，不能让已入库项目引用尚未提交的临时对象；无关或未审的项目不会随关联资料悄悄入库。共享基础资料仅指定维护人员可写（SPEC-006）；非维护人员提交导入时只可复用有效映射，缺失资料留待处理，不能借导入自动创建共享资料。

批量失败策略已确认（DEC-033，Q-022 已解决）：2026-09-30 用户选择“其余项目先入库，仅冲突项留待处理”。提交所选项时分别校验，各项可独立成功；冲突、失权、规则或引用异常项不入库，仍留在审查区并给出原因及恢复入口。结果显示成功数、待处理数和逐项结果，不以单一“成功”掩盖部分失败。成功项不因其他项失败回滚；重复请求或只重试失败项不得再次新增已经成功的项目。

大量数据可以由用户分次选择提交，具体单次限额及是否后台执行由真实规模与测量确定，不因“批量”直接增加 Redis。原有覆盖/叠加策略尚未收敛；逐卡片通过不能被实现为默认整库覆盖，完整数据库恢复仍按维护流程另行处理。

单个项目及其必要关联、审计、待审项成功结果作为一个短事务提交；其中任一步失败，该项整体回滚，不能留下只有主表或没有审计的半个项目。已存在的共享基础资料通过映射复用；新资料按明确维护权限、唯一性及引用约束写入，不能因另一项目失败而删除已经被成功项目引用的资料。共享引用异常时分别阻止依赖该引用的项目，给出具体关联原因；独立项目仍可成功。

批次保存各项实际结果；进程中断或断线后先查已提交结果，再决定重试，尚未执行项仍可接续。不得把收到任务 ID、请求返回或本地选择状态显示成全部正式入库成功。部分成功只适用于本节按项目选择入库，不能外推成整库覆盖或恢复可以半途成功。

验证：新请求逐项读回，项目数、关键值、关联和历史对账，再核对看板及导出。

建议删除先进入回收站；恢复重新校验引用和版本。完整数据库恢复与普通项目恢复分开，前者按运维流程执行，不开放为随手点击的业务按钮。

## SPEC-010 后台任务与重试
