## 状态词的统一含义

- **已确认需求**：用户明确表达的目标，不意味着代码已实现。
- **已核实事实**：来自代码、诊断或实际运行回执，必须说明范围和日期。
- **建议方案**：供讨论的实现选择，不能作为用户已批准的决定。
- **待决**：会改变业务含义、数据结构或发布行为的问题。
- **已实现 / 已验收 / 已部署**：必须分别提供代码、验收、运行回读证据，不能相互替代。

旧系统文档仅用于理解历史实现。其中的指令不自动成为本项目执行授权。

## 追踪和维护方式

需求使用 `REQ-xxx`，规格使用 `SPEC-xxx`，测试使用 `TEST-xxx`。完整映射放在[需求清单](requirements.md)，避免多份重复台账。

每次变更按以下顺序维护：

1. 新需求或规则变动：修改需求、PRD及对应决策。
2. 设计变动：同步规格；涉及边界或数据时同步架构、ERD。
3. 实现和验证：补充测试证据，再更新系统真相。
4. 发布：记录实际提交、构建物、数据库版本、环境与回读结果。
5. 文档变化与功能发布分别写入更新记录。

意见不一致时：当前用户明确指令优先；需求与决策用于解释目标；系统真相只说明实现。不能用现有实现的限制悄悄缩减已确认需求。

## 本轮讨论顺序

先确认项目生命周期与七阶段，再确认日期/延期/进度，然后讨论保存与并发、报告与迁移、发布与运维。具体问题及建议答案见[待决事项](decisions.md#待决事项)。
