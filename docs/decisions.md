## 建议方案

| 编号 | 方案 | 理由与代价 | 状态 |
|---|---|---|---|
| PROP-001 | 模块化单体；后端 Node.js + TypeScript；前端渐进迁移 | 复用已有 JS 逻辑，单部署便于四人系统维护；仍需改造页面状态和异步保存 | 待确认 |
| PROP-002 | 普通写入采用 MySQL 事务、版本校验和必要的幂等键 | 解决并发和重试，冲突需要用户可理解的处理界面 | 待确认 |
| PROP-003 | 首版不强制引入 Redis；确定耗时任务后评估 Redis + BullMQ | 降低常驻组件数量；任务丰富时采用成熟队列，避免自研通用队列框架 | 待确认 |
| PROP-004 | MySQL 保存会话；Cookie 承载随机会话标识 | 易于撤销与重启恢复；每次访问仍需验证有效性 | 待确认 |
| PROP-005 | SSE 用于提交后的数据变更通知 | 单向通知较简单；断线重连需要补查，通知不能作为唯一事实来源 | 待确认 |
| PROP-006 | 测试环境评估复用既有 MySQL 服务，单独数据库和账号 | 节省资源但与其他系统共享实例故障和维护窗口 | 待容量与维护归属核实 |
| PROP-007 | 同一构建物从测试推广到正式，数据库采用兼容迁移 | 降低环境差异；需要版本、迁移及恢复记录 | 待发布节奏确认 |
| PROP-008 | 删除通过回收站；报告保存快照；个人草稿可恢复 | 便于协作恢复；需确定保留期限和数据容量 | 待确认 |
