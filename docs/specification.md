# 系统规格书

版本：D0.1；日期：2026-09-29；状态：候选行为契约。除已确认需求外，具体规则均待对应决策确认。

## 通用约定

- API 路径为接口设计草案，当前没有这些接口。
- 请求身份由服务端会话解析，客户端不能提交 actor_id 冒充操作人。
- 写请求只接受白名单字段，明确校验规则。服务端生成提交时间与新版本。
- 校验独立输入后再修改数据；失败不改变业务和审计状态。
- 返回统一错误码、可理解信息、request_id，保留用户输入。400 为输入结构错误，401 为未认证，403 为禁止操作，404 为对象不存在，409 为版本/业务冲突；暂定 422 表示业务字段校验失败。
- 文档中的“必须”用于规定目标实现，不表示今天已具备该能力。

## SPEC-001 身份认证与会话

输入：登录名与凭据。前置条件：账号启用且未触发限速。

处理：验证密码哈希，创建随机会话；持久存 token_hash，安全 Cookie 保存随机标识。Cookie 使用 HttpOnly、Secure、明确 SameSite；写接口校验 CSRF。失败响应避免泄露账号是否存在。

输出：本账号身份和会话有效信息。登录态恢复仍需服务器验证，退出、改密、停用按策略撤销会话。会话期限与多设备策略见 Q-010。

接口草案：`POST /api/auth/login`、`POST /api/auth/logout`、`GET /api/me`。未认证请求不得读取业务数据和报告下载。

## SPEC-002 保存、事务、并发与审计

输入：业务动作参数、expectedVersion；创建及可重复副作用动作携带幂等键。

处理：读取并校验 → 在事务内按 ID 与版本条件更新 → 写业务子表和审计 → 提交 → 返回新版本。更新行数不满足预期时回滚并返回冲突，不静默覆盖。

幂等键按用户和操作范围约束；同键同请求返回原结果，同键不同内容返回冲突。幂等结果与业务提交的一致性必须有测试。

失败：数据库或审计失败时回滚；响应丢失后允许安全重试。409 保留本地草稿，重新获取版本后展示差异，不默认自动合并。

接口草案：`PATCH /api/projects/{id}` 仅更新普通字段；生命周期变化通过专用动作。项目级 version 统一保护子对象写入，初期接受较粗的冲突范围。

## SPEC-003 项目生命周期与阶段

动作草案：createProject、startProject、pauseProject、resumeProject、completeStage、closeProject、setMaintenance。

每个动作校验当前状态、版本、必要说明和关联数据，使用 SPEC-002 提交；跨状态操作不能靠任意字段 PATCH 绕过。

| 动作 | 候选规则 | 待决项 |
|---|---|---|
| 启动 | 明确责任人与有效计划；是否由 S1 完成自动触发待定 | Q-001 |
| 完成阶段 | 当前阶段、前置阶段满足、完成说明有效；重复提交不重复推进 | Q-002 |
| 暂缓 | 记录原因与时间，保留计划和已有成果 | Q-004 |
| 恢复 | 复核计划后继续；不自动抹去暂停期间历史 | Q-004 |
| 正常结案 | 确认交付条件和未完事项处置；不强制把实际未完阶段改为完成 | Q-003 |
| 中途终止 | 记录原因、终止时阶段、遗留风险及节点 | Q-003 |
| 开启量产维护 | 仅已结案可用，不自动重开研发 | 延续原业务含义 |

正常前台按序推进；导入历史数据必须单独校验，不能用普通页面不可点击作为数据库有效性的保证。

## SPEC-004 日期、计划和派生状态

候选模型：original_due_date 保留原始计划，current_due_date 代表现行计划，schedule_changes 记录改期过程。补充说明与有效改期有不同语义。

`rescheduleProject` 必须提交有效新日期及原因。追加说明不得修改 current_due_date。历史最后一条为空不能导致当前计划丢失。

候选逾期公式：项目处于需要追踪交付的状态且公司业务日期晚于有效计划日期。没有有效日期时显示“计划未定”，不能默认为正常。暂缓是否参与由 Q-004 决定。

历史改期、当前逾期和人工风险分别提供字段与解释。看板、详情、统计、导出调用同一领域规则；不在各页面复制不同公式。

阶段进度映射是否沿用原 5/10/20/60/80/90/100，以及跳过、终止的显示方式待 Q-002、Q-003。先补规则再固定测试。

## SPEC-005 风险、节点、变更和检查

风险新增保存内容和等级；解除保存处理结果、操作人和时间，保留原始内容。责任人、审批或复开行为待 Q-012。

节点包含项目/客户类型、目标日期、完成结果；连线与阶段引用必须属于当前项目。需求变更保留原事实和决定；是否进一步联动计划由规则确认，不能隐式改日期。

访问详情不更新业务检查记录。建议 `confirmCheck` 明确提交结论，产生 project_checks 记录；检查状态是派生结果，不覆盖业务更新时间。Q-006 未确认前标记为建议。

## SPEC-006 基础资料与引用

用户维护客户、工程师、芯片、产品线、APP、标签、分组和企业信息。新项目使用稳定 ID 引用；页面展示名称。

改名后当前展示可更新，历史审计保留当时名称；停用后旧项目仍可读取，新选择器默认不提供停用项。有引用的数据禁止直接级联删除。

旧系统名称映射沿用 NFKC、大小写和空白归一化作为候选匹配依据，但冲突必须明确展示，不把不同人员或芯片静默合并。

## SPEC-007 工作状态与草稿

偏好按用户和页面保存；滚动位置可按设备/标签页保留，避免另一设备反复覆盖当前阅读位置。刷新或返回优先恢复界面，再校验业务版本。

草稿保留 base_version，不能直接覆盖正式数据。重新登录后仅同一账号可恢复。账号切换清理本机敏感缓存；服务端草稿的保留期限待确认。

网络中断不显示已保存；恢复后检查身份与版本再提交。新版本提醒不强制刷新正在编辑的页面。

## SPEC-008 会议、统计与报告

报告输入包含项目范围、字段、筛选、报告名称及格式。建议固定生成时快照，记录生成账号和时间；导出读取相同快照，避免过程中读取多个不同版本。

多行状态、人员、芯片、维护标识、项目备注等按选择输出。HTML/Markdown/CSV 各自正确转义，CSV 需评估公式注入处理且不破坏业务原文。下载结果可追溯并受认证保护。

会议开始、暂停、继续、结束均是业务动作；计时依据保存的时间点，浏览器关闭不丢会议。会议与报告的最终数据结构仍需 Q-012 确认。

结果必须可下载或供下一步汇报消费。任务状态成功但产物无法下载不算完成。

## SPEC-009 导入、迁移与删除恢复

输入：旧 JSON 原文件、明确来源、备份 schema 版本和冲突策略。

预检：容器结构、语义 ID 重复、名称引用、非法阶段、缺失日期、旧字段及业务备注；输出逐项映射和未解决项。无预检确认不得执行覆盖导入。

提交：限定导入范围；对小批量以事务整体提交，失败回滚；大批量策略待数据规模确认。导入与在线编辑冲突需检查版本或在明确维护窗口执行。

验证：新请求逐项读回，项目数、关键值、关联和历史对账，再核对看板及导出。

建议删除先进入回收站；恢复重新校验引用和版本。完整数据库恢复与普通项目恢复分开，前者按运维流程执行，不开放为随手点击的业务按钮。

## SPEC-010 后台任务与重试

仅在确认任务需要异步时实施。任务状态：queued → running → succeeded / failed；失败可按策略重试，具体重试次数、超时及保留期限待任务类型确定。

收到任务 ID 仅表示已受理，不表示完成。状态接口必须给出任务类型、发起人、进度含义、结果和可用恢复动作。

若使用 Redis + BullMQ：提交与投递之间可恢复、任务执行幂等、产物写入有确定标识、进程崩溃可重试；同一任务不能重复改业务、重复生成被误认为不同的记录。重任务与交互请求分进程，限制并发。

未引入队列时不编写空的队列适配框架。需求明确后依据实测选型。

## SPEC-011 部署、升级与恢复

测试入口公网 HTTPS，前后端同站点；MySQL 和可选 Redis 内部访问。账号和数据库凭据通过运行配置注入，不进入 Git。

版本化构建物包含代码提交标识；数据库迁移有独立版本。升级先验证备份和兼容性，再迁移、部署、检查健康、执行真实业务回读。

应用回退使用上一可兼容构建物；数据库恢复需独立方案，不能自动覆盖发布后数据。更新策略详见[发布维护](release-maintenance.md)。

## SPEC-012 性能与容量

以下为建议目标，待 Q-007、Q-011 及代表性数据确认后成为发布门槛：

| 指标 | 候选目标 | 测量范围 |
|---|---|---|
| 已加载列表的筛选/视图切换 | 交互反馈约 100 ms 内 | 浏览器本地，不含首次数据获取 |
| 普通业务 API | 服务端处理 p95 ≤ 200 ms | 排除导入、报告等重任务，包含正常数据库访问 |
| 普通保存 | 公司实际网络下多数请求力争 1 秒内确认 | 包含网络与提交，必须记录分布 |
| 多人场景 | 4 个独立会话同时操作 | 真实事务、状态更新、冲突及通知 |

测试报告记录数据规模、预热、持续时间、请求数、p50/p95、错误率、服务器资源和网络。首次登录、冷启动和大历史详情单独测量。现有服务器共享其他负载，未压测前不声明容量通过。

## SPEC-013 文档、模块和验收治理

每条变更对应 REQ、SPEC、TEST；规则变动先维护决策。模块测试通过稳定公开接口验证业务结果，避免依赖内部调用次数或私人函数名。

完整业务证据包含输入来源、实际动作、持久化、独立请求读回、后续页面/报告消费。新模块只暴露必要能力；跨模块写入及原始 SQL 访问有明确归属。

文档变更不能记成功能发布；代码提交、测试通过、部署成功和用户验收分别记录。
